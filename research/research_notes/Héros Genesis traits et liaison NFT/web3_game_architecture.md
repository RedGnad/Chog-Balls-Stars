## What the earlier game (chogtanks-mclip-main-3) wallet integration does, and what can be reused for Monad mainnet

### Takeaway
The earlier game connects a wallet with Reown AppKit Unity 1.4.1 on Monad testnet, asks for a constant `personal_sign` message that is never verified by any server, gates NFT features purely on the client, and identifies players to its backend with an anonymous Firebase token plus a client-declared wallet address. The AppKit bootstrap, the custom `Chain` object, the `ReadContractAsync` usage and the Brotli header file are reusable; the trust model (no server-side proof of wallet control, client-side gating, enumerable-only NFT listing, testnet endpoints, file-based server state) is not.

### Inferences
- **INFERRED** The earlier flow proves nothing to a server: a modified client can claim any address, because wallet control is only "proved" by a local PlayerPrefs flag and the backend identity is an anonymous Firebase uid. For a game where career and purchases attach to an NFT, the signature must be verified server-side with a nonce (see the authentication question).
- **INFERRED** `customWallets` and `connectViewWalletsCountMobile` did not reach the WebGL modal in 1.4.1 (the bridge does not forward them), so on mobile browsers the wallet list and deep links were those of the web AppKit filtered by `includedWalletIds` / `excludedWalletIds`. The same is true in 1.7.1 (see next question).
- **INFERRED** `CheckAnyTokenERC1155` cannot work on Monad mainnet: at one block per 300 ms a scan from block 0 in 100-block chunks is more than one million requests, and a past `TransferSingle` does not prove current ownership.
- **INFERRED** The voucher scheme (`MINT` / `EVOLVE`) is replayable across contracts or chains that share the same signer because the signed tuple has no chain id and no contract address; an EIP-712 domain fixes this.
- **INFERRED** Reusable as is, after changing constants: the `AppKitConfig` + custom `Chain` pattern (chain reference `"143"`, mainnet explorer, an RPC URL without a secret), the `OpenModal` then `SignMessageAsync` sequence, `ReadContractAsync` with human-readable ABI for client display, the header-secret check on Photon webhooks, per-route rate limiting, the `vercel.json` compression header pattern. To rewrite: message format (EIP-4361), server-side verification, identity (wallet from the verified session instead of Firebase anonymous + body field), NFT listing (the Genesis collection is not enumerable), webhook routes and payloads (Quantum 3 uses `X-SecretKey` and `/game/create`, `/player/add`, etc., `quantum3 note:42-53`), storage (JSON file and in-memory maps do not survive serverless or multi-instance hosting).

## Reown AppKit for Unity in October 2026

### Takeaway
The latest Unity AppKit is 1.7.1 (2026-09-03), minimum Unity 2023.1, with no statement about Unity 6000.6; on WebGL it is a thin bridge that loads the web AppKit (`@reown/appkit-cdn@1.8.23`) from jsDelivr and routes EVM calls through Wagmi. Monad mainnet needs a custom `Chain` object with your own RPC URL (not a predefined chain, not served by Reown's RPC proxy), and SIWE / One-Click Auth are explicitly not supported on WebGL, so sign-in must be built with `AppKit.Evm.SignMessageAsync` plus a backend.

## Authentication flow: SIWE or SIWX, nonce, replay, session tokens, smart-contract wallets, and mapping to Photon custom authentication

### Takeaway
Use a backend-driven EIP-4361 sign-in (server nonce, domain and chain id checks, expiry), verify with viem's `publicClient.verifyMessage` / `verifySiweMessage` on chain 143 so EOAs, ERC-1271 wallets and ERC-6492 counterfactual wallets all work, then issue a short session token that the client passes to Photon custom authentication; the Photon auth endpoint answers with `UserId` = wallet address and a secret `AuthCookie`, which every Quantum webhook then carries.

### Cited Findings
- **VERIFIED** EIP-4361 message: begins `[ scheme "://" ] domain %s" wants you to sign in with your Ethereum account:"`; required fields are domain, address, uri, version, chain-id, nonce, issued-at; optional are scheme, statement, expiration-time, not-before, request-id, resources. The nonce is "used to prevent replay attacks, at least 8 alphanumeric characters" (`nonce = 8*( ALPHA / DIGIT )`). "A `nonce` SHOULD be selected per session initiation with enough entropy to prevent replay attacks." Wallets "MUST prevent phishing attacks by verifying the origin of the request against the `scheme` and `domain` fields." For EOAs "the verification method specified in ERC-191 MUST be used."; for contract accounts "The verification method specified in ERC-1271 SHOULD be used". The EIP text does not mention ERC-6492. (Fetch-tool extraction.) [Source](https://eips.ethereum.org/EIPS/eip-4361)

### Inferences
- **INFERRED** Recommended flow (a design proposal, not a documented reference implementation):
  1. `POST /auth/nonce` returns `generateSiweNonce()`; the server stores it with a 5 minute expiry, single use.
  2. Unity builds the EIP-4361 text with `domain` = page host, `uri` = page origin, `version` 1, `chainId` 143, the nonce, `issuedAt`, `expirationTime`, and a statement naming the game; it signs with `AppKit.Evm.SignMessageAsync`.
  3. `POST /auth/verify { message, signature }`: `parseSiweMessage`, then `publicClient.verifySiweMessage({ message, signature, domain, nonce })` on a Monad client; reject wrong chain id, unknown or consumed nonce, wrong domain, expired message; mark the nonce consumed in the same write; issue a signed session token (for example a JWT with `sub` = lowercase address, `sid`, `exp` at most 1 hour to match Photon's ticket).
  4. Unity sets Photon `AuthValues` to `CustomAuthenticationType.Custom` and sends the session token through `AuthPostData` (JSON body) so it does not sit in a query string.
  5. The Photon auth endpoint checks the dashboard-only secret pair and the token, then answers `{ ResultCode: 1, UserId: <lowercase address>, AuthCookie: { wallet, sid, iat } }`; any failure answers `ResultCode: 2`. Dashboard: reject anonymous clients and reject when the provider is offline.
  6. Each webhook (`/game/join`, `/player/add`, `/game/result`) reads the wallet from `AuthCookie`, never from client fields.
- **INFERRED** Canonical form matters: Photon `UserId` is an opaque string, so mixed-case (EIP-55) and lowercase forms of one address would be two users; always lowercase.
- **INFERRED** Replay analysis: the nonce defeats replay of the sign-in; domain binding defeats cross-site phishing only if the wallet shows or checks the origin; `chainId` 143 prevents reuse on another deployment; the session token must be bound to the nonce id (`sid`) so it can be revoked; a stolen session token is usable until expiry, hence the short lifetime.
- **INFERRED** Verification must run against a Monad RPC (not offline `ecrecover` only), otherwise Safe multisigs on Monad and EIP-7702 or smart-account users are rejected. With email and social login disabled, counterfactual ERC-6492 signatures are unlikely but `verifyMessage` handles them anyway.
- **INFERRED** SIWX adds nothing for this game: it is the chain-agnostic generalisation (CAIP-122) used by the web AppKit plugin, not available in the Unity SDK, and the game has one EVM chain.

- **INFERRED** Delegation today: no delegate.xyz v2 on Monad mainnet. ## Purchases with an ERC-20 ($CHOG): contract patterns, fulfilment, finality, idempotency, refunds, gas sponsorship, security pitfalls

### Takeaway
A small shop contract that pulls `$CHOG` with `SafeERC20.safeTransferFrom`, records the entitlement against the token id and emits an event is enough; `$CHOG` exposes the EIP-2612 surface on chain, so "permit plus buy" in one transaction is plausible with "approve plus buy" as the fallback. - **INFERRED** Pattern comparison:
  - Approve plus `transferFrom`: two transactions on first purchase (or one approval of a larger amount, which leaves a standing allowance on an unverified token contract). Works with every wallet. Baseline and fallback.
  - EIP-2612 permit: one signature plus one transaction (`buyWithPermit`), no standing allowance. The selector and helper functions are present in the `$CHOG` implementation, but the source is unverified and `eip712Domain()` reverts, so the EIP-712 domain `name` and `version` must be recovered by matching the on-chain `DOMAIN_SEPARATOR` and a real permit must be tested with a dust amount before shipping. Wrap the permit in try/catch as OpenZeppelin recommends.
  - Permit2: the user must first approve Permit2 on the token (one transaction), after which each purchase is one signature plus one transaction and the witness can bind `(tokenId, skuId, price)`. No gain over native permit when the token has it; useful if the permit test fails.

- **INFERRED** Shop contract shape (proposal): `buy(uint256 tokenId, uint256 skuId, uint256 maxPrice)` and `buyWithPermit(...)`; checks `skuId` is active and `price <= maxPrice`; optionally requires `IERC721(genesis).ownerOf(tokenId) == msg.sender` (or deliberately allows gifting); pulls the price with `safeTransferFrom(msg.sender, treasury, price)`; verifies the treasury balance increased by exactly `price` (the token is unverified, so a transfer fee cannot be excluded); sets `owned[tokenId][skuId] = true` and reverts if already set; emits `Purchased(buyer, tokenId, skuId, price)`. ## Hosting and delivery of the Unity WebGL build as an installable PWA; wallet deep links from an installed PWA

### Takeaway
A static host with correct `Content-Encoding` and `application/wasm` headers is sufficient, and the current prototype build (12.7 MB gzip, largest file 9.4 MB) fits every host's per-file limit including Cloudflare Pages' 25 MiB. Unity's built-in PWA template gives a manifest and a cache-first service worker that must be customised before production, and on iOS an installed PWA cannot be the return target of a wallet link, so the dependable mobile path is to open the game inside the wallet's in-app browser.

### Inferences
- **INFERRED** Recommended delivery: Cloudflare Pages with the Unity build compressed by Unity (gzip as today, or Brotli for a smaller download since the site is HTTPS), "Name Files As Hashes" enabled, and a `_headers` file setting `Content-Encoding` and `Content-Type` for `/Build/*.gz` or `/Build/*.br` plus long-lived `Cache-Control` for hashed files and `no-cache` for `index.html`. Pre-compression is needed because the `.data` file is `application/octet-stream`, which Cloudflare does not compress on its own. Keep each file under 25 MiB; the present build has a large margin, but watch the `.wasm` once Reown, Nethereum and Minimal stripping are added.
- **INFERRED** The stock PWA service worker is unsafe for this game as shipped: it would cache `index.html` and any GET to the backend (nonce, career, entitlements) forever and serve stale data, it never deletes old caches, and it would also cache the cross-origin AppKit bundle. Replace it with a worker that caches only same-origin hashed build files, uses network-first for `index.html`, and bypasses everything else (API hosts, RPC, jsDelivr, WalletConnect relay).
- **INFERRED** itch.io is a poor fit for the wallet build: the game runs in an iframe on a third-party origin (EIP-4361 domain binding, injected providers and Safari IndexedDB in iframes all become problems). GitHub Pages forbids commercial SaaS use, which a token shop arguably is. Netlify's free credits cap bandwidth at 15 GB per month if nothing else consumes credits.
- **INFERRED** Wallet behaviour from an installed PWA: on iOS a universal link back to the game URL opens Safari (or an in-app browser view), not the installed app, because link capturing is unsupported, and the installed app has storage separate from Safari, so a session created in one is absent in the other. After approving in the wallet app the player must switch back to the PWA by hand, and the WalletConnect session must survive the app being backgrounded. On Android Chrome the installed PWA shares the browser profile and is more forgiving. The dependable mobile path is a button "Open in wallet" that uses the wallet's dapp deeplink so the game runs in the wallet's in-app browser with an injected provider; PWA installation then matters mostly for desktop and for players using WalletConnect deliberately.
- **INFERRED** Mobile viewport: Unity's templates set `user-scalable=no`, the setting a reporter linked to a broken AppKit connection UI on mobile (issue #178). Test with and without it before blaming the wallet.

## Component list for the recommended architecture, simplest production-grade option and free-tier estimate

### Takeaway
Everything except gameplay networking fits on one static host, one serverless backend with a small SQL database, one small contract and direct RPC reads: no mandatory indexer, no custom chain infrastructure. At the scale of 1,969 heroes the free tiers of Cloudflare (Pages, Workers, D1 or Durable Objects) cover a first release, with the Workers 10 ms CPU limit and the 100,000 requests per day as the first ceilings to watch.

### Cited Findings
- **VERIFIED** Capabilities the Photon side gives the backend: reject or accept at custom authentication, `JoinGame` and `AddPlayer`; replace `RuntimePlayer`, `RuntimeConfig`, `SessionConfig`; receive an untrusted aggregated `GameResult`; receive the server-side input stream for re-simulation (`quantum3 note:12-24`, `:238-250`).
- **VERIFIED** Free-tier figures used below: Cloudflare Pages 25 MiB per file and 20,000 files; Workers 100,000 requests per day and 10 ms CPU per invocation, paid from $5 per month; D1 5 million rows read and 100,000 rows written per day, 5 GB; Durable Objects (SQLite) 100,000 requests per day; KV 1,000 writes per day; Neon 100 CU-hours and 1 GB per project; Monad public RPC 25 requests per second on `rpc.monad.xyz`; Monad fees about 0.0065 MON for a 65,000-gas transaction. [Source](https://developers.cloudflare.com/pages/platform/limits/); [Source](https://developers.cloudflare.com/workers/platform/pricing/); [Source](https://neon.com/pricing); [Source](https://docs.monad.xyz/developer-essentials/network-information/index.md); [Source](https://docs.monad.xyz/developer-essentials/gas-pricing.md)
- **VERIFIED** Deployment cost reference on Monad: "deploying the contract is a one-time cost of roughly 0.25 MON" (for the ERC-721 example of the guide). [Source](https://docs.monad.xyz/guides/build-with-nfts.md)

### Inferences
- **INFERRED** Components (each line: role; simplest production-grade option; free-tier estimate; main caveat):
  1. Client. Unity 6000.6 WebGL with Reown AppKit Unity 1.7.1, custom `Chain` for `eip155:143`, email and social login off, EIP-4361 message built in C#, `ReadContractAsync` for `tokensOfOwner`, `WriteContractAsync` for the shop. Free SDK. Caveat: compatibility with 6000.6 and `.wasm` growth are unmeasured.
  2. Static hosting. Cloudflare Pages, Unity-compressed files, `_headers`, custom service worker. Free: 25 MiB per file (largest file today 9.4 MB), 20,000 files (17 today), 500 builds per month. Caveat: verify `Content-Encoding` handling on a real deployment.
  3. Auth service. One Worker: `/auth/nonce`, `/auth/verify` (viem `verifySiweMessage` on chain 143), and the Photon custom authentication endpoint returning `UserId` and `AuthCookie`. Free: 100,000 requests per day; a login costs 3 requests plus 1 RPC call. Caveat: signature recovery plus JSON work must fit 10 ms of CPU on the free plan; otherwise the $5 plan.
  4. Nonce and lease store. D1 table or a SQLite Durable Object (not KV: 1,000 writes per day free). Free quotas are far above need.
  5. Ownership index. None for admission: `ownerOf` at `finalized` through a Monad RPC inside the `/player/add` handler; `tokensOfOwner` once per login; optional three-call Multicall3 snapshot cached in the database for galleries. Free on public RPC at 25 rps; use a keyed provider endpoint for production reliability. Caveat: the worst-case `tokensOfOwner` (16.5M gas) uses the limited high-gas pool.
  6. Career database. D1 (or Neon Postgres if relational tooling or a non-Cloudflare worker needs it), schema from the persistence question, idempotent on game id. Free: 100,000 row writes per day on D1; a 10-player match writes on the order of 30 to 50 rows.
  7. Shop contract. One non-upgradeable Solidity contract on Monad: SKU price table, `buy` and `buyWithPermit`, `owned[tokenId][skuId]`, `Purchased` event, OpenZeppelin `SafeERC20`, re-entrancy guard, `Ownable2Step`, `Pausable`. Cost: a fraction of a MON to deploy. Caveat: `$CHOG` source is unverified, test permit and transfer behaviour with dust first.
  8. Purchase indexer. Optional. Entitlements are read from contract state at admission; a scheduled reconciliation job tails `Purchased` logs at `finalized` in 100 or 1,000 block windows (2,880 or 288 calls per day) into an `entitlement` table keyed on `(tx_hash, log_index)` for receipts and support.
  9. Photon webhooks backend. Same Worker: `/game/create`, `/game/join`, `/game/configs`, `/player/add`, `/player/added`, `/player/removed`, `/game/result`, `/replay/start`, `/replay/chunk`, `/game/close`, each checking the `X-SecretKey` header and reading identity from `AuthCookie`. Free-tier estimate: about 45 control-plane requests per 10-player match, plus one replay chunk every 20 seconds by default (about 45 for a 15 minute match), so about 90 requests per match and roughly 1,100 matches per day inside 100,000 requests; raising the replay interval to its 40 second maximum (`quantum3 note:43`) roughly halves the replay share.
  10. Re-simulation worker (dependency inherited from the Photon note, not a web3 component). A .NET process cannot run on Workers; it needs a container or small VM and access to the stored replay stream. Career credits stay provisional until it exists.
- **INFERRED** Data flow summary: wallet connect, then sign-in (nonce, EIP-4361, verify, session token), then Photon connect with the token (custom auth sets `UserId` and `AuthCookie`), then room entry, then `AddPlayer` webhook (ownership at `finalized`, token lease, entitlements from the shop contract, server-built `RuntimePlayer`), then match, then `GameResult` and replay (adjudication), then idempotent career write keyed by game id and token id. Purchases are an independent loop: wallet transaction to the shop, wait for `finalized`, backend re-reads contract state.
- **INFERRED** What stays on-chain: Genesis ownership, `$CHOG` payments, purchased specialisations bound to the token id. What stays off-chain: sessions, matches, results, experience, statistics, leases. Optional later: Merkle root or checkpointed level.
