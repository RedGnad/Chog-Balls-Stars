Research date: 2026-10-08. Project baseline given by the caller: Quantum 3.0.9 (build 1932), Unity 6000.6.4f1, WebGL, IL2CPP.

## Key question 1: Is Quantum 3 officially supported on WebGL and mobile browsers, and with which caveats?

### Takeaway
WebGL is an officially listed Quantum 3 platform ("special considerations" apply) and Unity 6 lists Android Chrome 58+ and iOS Safari 15+ as supported mobile browsers; but Photon states WebGL performance is lower, the simulation is confined to the main thread (ThreadCount ignored) unless Unity 6 experimental multithreading is enabled, transport falls back to WebSockets/TCP, and Photon explicitly recommends also shipping a downloadable build. Unity 6000.6 is not in Quantum's published compatibility table (which stops at 6000.5).

## Key question 2: What does the per-client simulation cost consist of (verified + predicted + rollbacks), and what drives it (rate, entities, physics, navmesh, bots)?

### Takeaway
Every client runs the full deterministic simulation twice over: verified frames advance only when the server confirms all players' inputs for a tick, and on every session update Quantum rolls back to the latest verified frame and re-simulates forward to the predicted head (depth roughly RTT/2 in ticks plus clock effects), regardless of whether a misprediction was detected. Cost therefore scales as (verified ticks advanced + predicted depth) x per-tick cost, where per-tick cost scales with entity count, physics entries and interactions, navmesh agents, and AI. Official levers: Prediction Culling (cull entities outside a sphere from predicted frames), lower Simulation Rate, physics sleeping/layers/kinematics, ChecksumInterval 0, Release DLLs + IL2CPP.

### Cited Findings
- VERIFIED: "Quantum always rolls-back and re-simulates frames. It is a necessity for determinism and involves the validation of player input by the server." A verified frame requires "the input from ALL players is confirmed by the server for this tick" and all previous ticks verified; "the verified simulation only simulates the next verified frame once it has received the server-confirmed inputs; as such, it moves forward proportional to RTT/2 from the server." Predicted frames advance "as soon as the simulation has accumulated enough delta time in the local session". [Source](https://doc.photonengine.com/quantum/current/manual/frames)
- VERIFIED: Rollback flow: "The local client collects input. Quantum predicts future frames. Verified input arrives from the network. Quantum rolls back to the latest verified frame. The simulation re-runs from that frame to the current predicted state. Quantum performs this rollback and re-simulation as part of its normal prediction model. This provides consistent simulation behavior and makes performance easier to profile than a system where rollback occurs only after detected input differences." [Source](https://doc.photonengine.com/quantum/v3/video-tutorials/prediction-culling)

### Inferences
- INFERRED cost formula per Unity frame on a single-threaded WebGL client: T_sim = (V + P) x t_tick, where V = verified ticks newly confirmed since last update, P = predicted depth re-simulated = (PredictedFrame.Number - VerifiedFrame.Number), which the docs tie to RTT/2 and the local input offset; at 60 Hz and 100 ms RTT, P is about 3 ticks plus clock skew, at 60 Hz and 300 ms RTT about 9 ticks, bounded by RollbackWindow (60). With culling, the P term applies only to entities inside the prediction sphere; the V term always covers all entities.
- INFERRED: Halving Simulation Rate (60 to 30 Hz) halves both V and P for a given RTT, so it roughly halves simulation CPU, at the price of 33 ms input granularity; the docs explicitly endorse lowering the rate as far as gameplay allows.
- INFERRED: On WebGL the default ThreadCount = 2 is irrelevant (ignored); physics and navigation tasks that are normally spread across workers all land on the main thread, so the Task Profiler timings taken on desktop multi-core are not transferable to the browser; measure on device.
- INFERRED: Memory: the rollback ring buffer allocates RollbackWindow frames of the full frame heap at start (FAQ), so 60 frames x (entity memory + 8 MiB default heap pages, lazily used) is a real pressure point on a 32-bit WebAssembly heap; reducing RollbackWindow (for a 30 Hz MOBA, 30 to 40 frames would still cover 1 s of prediction) and HeapPageCount are the documented knobs. The exact per-frame memory footprint is not documented.

## Key question 3: How does a skillshot feel under Quantum (local input immediate or delayed, rollback on remote entities, prediction culling), compared with a server-authoritative interpolated model?

### Takeaway
With default settings (InputDelayMin = 0, InputDelayPingStart = 100 ms) the local player's input is applied in the next predicted tick with no artificial delay while ping is below 100 ms; above that the server grows the client's input offset dynamically (up to 60 ticks). Remote players are extrapolated by repeating their last Repeatable input, so a skillshot cast or dodge by a remote player appears late by roughly the remote player's upload path plus confirmation, and shows up as a visible correction (lerped by the view's error correction, or snapped if beyond teleport thresholds). Hits are resolved by the deterministic simulation itself (verified frames are identical on all clients); there is no lag compensation layer in the docs, so a locally predicted hit on an extrapolated remote entity can be rolled back.

### Cited Findings

[Source](https://doc.photonengine.com/quantum/current/quantum-intro)
- VERIFIED: "Quantum predicts gameplay ahead of the latest verified frame. This allows local input to affect gameplay immediately instead of waiting for a network round trip." [Source](https://doc.photonengine.com/quantum/v3/video-tutorials/prediction-culling)

### Inferences
- INFERRED: Default feel for the local caster: zero added input delay below 100 ms ping; the projectile spawns on the next predicted tick (16.7 ms at 60 Hz, 33 ms at 30 Hz) and its view can appear immediately with Non Verified bind behaviour. Above 100 ms ping the input offset grows, so a 200 ms mobile connection will feel like a few ticks of added delay; the docs do not publish the offset-vs-ping curve.
- INFERRED: For remote targets, Quantum extrapolates (repeat last input) rather than interpolates behind, so a remote hero's dodge is first seen as a correction (slide or snap) about one way-trip plus confirmation later; in a server-authoritative interpolated model the remote hero is instead shown continuously but ~100 ms behind. Quantum's remote view is therefore "on time but sometimes wrong", the server-authoritative one is "late but never wrong"; Snapshot interpolation mode on remote heroes converts Quantum to the second behaviour at the cost of ping-proportional view latency.
- INFERRED: Hit resolution is purely the deterministic simulation: a skillshot hit computed in a predicted frame against an extrapolated remote position can be undone when verified input arrives (projectile may visibly "un-hit" or a hit VFX may need to be driven from verified frames or from events raised in verified frames). No lag compensation exists or is needed because there is no server-side hitscan; the "fairness" rule is simply whichever inputs the server confirmed for that tick.
- INFERRED: Adding 2 ticks of InputDelayMin (as the docs suggest trying) costs 33 ms at 60 Hz or 67 ms at 30 Hz of local latency but cuts predicted depth and rollback CPU, which is a lever specifically attractive on low-end WebGL.

## Key question 4: How do reconnection and late join work (who provides the snapshot, timeouts, PlayerTTL / EmptyRoomTTL)?

### Takeaway
On the Public Cloud a late-joiner or reconnecting client gets a "buddy snapshot" that the server requests from another connected client (load-balanced), with the session paused until it arrives (wait times out at 15 s; upload timeout 10 s, download timeout 20 s); server-generated snapshots require a custom plugin on the Enterprise Cloud. A client may instead restart from its own local snapshot if it is younger than 10 s (extended up to EmptyRoomTTL, max 2 min). Getting back into the room relies on Photon Realtime fast reconnect, which needs PlayerTTL > 0 (0 by default; 20 s suggested), the same UserId and the same Quantum ClientId; the QuantumRunner must be destroyed and recreated.
