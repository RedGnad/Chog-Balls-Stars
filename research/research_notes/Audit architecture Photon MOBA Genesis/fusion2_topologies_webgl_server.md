## Key question 1: What the fusion-choose page says about WebGL, mobile, and Shared vs Host vs Server

### Takeaway
Photon's official position (fusion-choose, updated 28/07/2026) is unambiguous: Shared Mode is "strongly" recommended on WebGL and is "the recommended mode for mobile"; Server and Host modes are "not recommended and by default disabled" on WebGL and must be explicitly enabled via "Enable ClientServer Modes in WebGL builds" in NetworkProjectConfig. Dedicated Server on mobile is "only recommended for high ARPU mobile titles".

### Cited Findings
- VERIFIED. WebGL section, verbatim: "We strongly recommend Shared Mode on WebGL. Using shared mode on WebGL provides much better latency than Host / Server because a direct connection to the cloud can be established. CPU usage is also much lower which is important due to WebGL running only on a single thread. Server and Host mode are not recommended and by default disabled." [Source](https://doc.photonengine.com/fusion/v2/fusion-choose)
- VERIFIED. Same section: "Though users can technically act as the server in WebGL builds, either through Dedicated Server or Client Host topologies, it is not recommended due to performance and networking limitations. Typically, WebGL runs on a single thread, which is suspended when the page is not in focus (background tab). While this is fine for individual players, suspending the server of a session will affect all players in a match. Additionally, if a WebGL build acts as the server, it will always utilize a relay connection since direct connections are not supported for WebGL builds." [Source](https://doc.photonengine.com/fusion/v2/fusion-choose)
- VERIFIED. The toggle: "To enable Server / Host Mode on WebGL toggle \"Enable ClientServer Modes in WebGL builds\" in the `NetworkProjectConfig` to true." [Source](https://doc.photonengine.com/fusion/v2/fusion-choose). The NetworkProjectConfig manual names the same setting "Allow Client Server Modes in WebGL" and explains: "By default, when using Client Server Mode, WebGL builds are disabled. They are not recommended since they can lead to degraded performance and Client Host are not reliable and often lead to disconnects in WebGL. If checked, this setting will allow Client Servers to be utilized despite these limitations." [Source](https://doc.photonengine.com/fusion/v2/manual/network-project-config)
- VERIFIED. Mobile section: "Fusion - Shared: The recommended mode for mobile. Due to Fusion's performance and speed, Shared Mode works well since the connection is to the cloud and not to other players directly. Shared Mode is also the only mode that does not need to run resimulations which in many cases reduces CPU usage." "Fusion - Dedicated Server: Is expensive to operate due to additional third party hosting costs for the servers. Only recommended for high ARPU mobile titles." "Fusion - Client Host: Host Mode is not recommended for mobile except for special use-cases. Because one of the players will also be acting as the server, having a poor connection can make this a difficult and unreliable solution for mobile. Mobile games also have the highest player quit rates which when the host quits the game will lead to a short break while migrating to a new host. On Mobile NAT Punchthrough success rates are lower than other platforms (mobile networks don't allow for this) which causes a lot of connections to be relayed over the cloud which adds additional latency." [Source](https://doc.photonengine.com/fusion/v2/fusion-choose)
- VERIFIED. Suggested game types: "Fusion - Dedicated Server: competitive games with a lot of users often work well in Server Mode due to their stronger cheat protection." "Fusion - Client Host: ... games with few players within a session (2-4), work well in this solution as well." "Fusion - Shared: This solution is good for more casual games or those with a lot of players, especially applications in which players will enter and leave often since doing so will not disrupt gameplay." [Source](https://doc.photonengine.com/fusion/v2/fusion-choose)
- VERIFIED. Cheat protection, verbatim: "Fusion - Dedicated Server: Cheat protection is strong because the dedicated server has state authority over the game. ... When using `NetworkInput` and `NetworkedProperties` for the gameplay cheating that affects the gameplay state such as speed hacks, or adjusting variables via memory modification is impossible. The only possible cheats in a well-designed Server Mode game are aimbots (A program instead of a user provides inputs) or wall-hacks (can be limited with object interest)." "Fusion - Client Host: ... The host client, can cheat and modify any value and has access to full information." "Fusion - Shared: Because players have State Authority over objects they control, cheating can occur without extra precautions being taken. This includes modifying any `NetworkedProperty` to any value or sending `RPCs` at any time and more." [Source](https://doc.photonengine.com/fusion/v2/fusion-choose)
- VERIFIED. Server complexity: "Setting up a dedicated server requires the headless server version of the game to run on servers managed by the user in-house or a third party server hosting solution, which requires more setup and costs much more to operate." [Source](https://doc.photonengine.com/fusion/v2/fusion-choose)
- VERIFIED. Cost: "CCU for all three Fusion solutions are the same. ... When using Server Mode, bandwidth pricing will depend more on the third party server provider." [Source](https://doc.photonengine.com/fusion/v2/fusion-choose)
- VERIFIED. The page offers no numeric latency figures; the only latency comparison is the qualitative WebGL sentence above (Shared "much better latency than Host / Server" on WebGL). Elsewhere, Host mode relay fallback is said to affect "approximately 1 in 10 players" and to be "rarely noticeable". [Source](https://doc.photonengine.com/fusion/v2/manual/network-topologies)
- VERIFIED. The separate "Fusion 2 Shared" doc set states: "Fusion Shared Mode leverages the Photon Cloud to run sessions and keep them alive until the last player leaves. This provides a scalable solution covering mobile and WebGL apps in the same way as standalone and console titles. At the same time, it saves the cost and effort of hosting dedicated server instances." [Source](https://doc.photonengine.com/fusion/2-shared/fusion-shared-intro)
- VERIFIED. Photon's own WebGL sample ("Fusion Crazy Starter WebGL", built for CrazyGames, v2.1.2 Sep 02 2026, Unity 6000.0.78f1) uses Shared Mode and says: "This sample utilizes Photon Fusion's Shared Mode topology ... For a more detailed explanation as to why Shared Mode topology is best for WebGL, refer to the Photon Fusion's documentation regarding network topology." It also states, for CrazyGames specifically: "running applications in multithreaded mode is not supported" and recommends "Run In Background property is set to true". [Source](https://doc.photonengine.com/fusion/v2/technical-samples/fusion-webgl)

### Inferences
- INFERRED. The "disabled by default" statement applies to WebGL builds running any Client/Server GameMode (Client, Host, Server, AutoHostOrClient), i.e. it also covers a WebGL CLIENT joining a non-WebGL dedicated server, because the NetworkProjectConfig text says "when using Client Server Mode, WebGL builds are disabled" and the toggle text says it "will allow Client Servers to be utilized". The fusion-choose sentence about the relay and background-tab suspension is written about a WebGL build acting as the server, but the "direct connections are not supported for WebGL builds" clause is a transport fact that necessarily applies to a WebGL client too (see KQ2 and KQ9).
- INFERRED. For a browser-first 3v3 MOBA the official guidance pushes to Shared Mode; the trade is explicit: lowest latency path on WebGL and no resimulation CPU, in exchange for no server authority (KQ5).

### Gaps
- No quantified latency numbers (ms) for any mode exist on the page.

## Key question 2: WebGL transport (WebSocket / WSS) and documented restrictions

### Takeaway
No Fusion 2 page states "WebGL uses WebSockets" in those words. The documented facts are: direct (UDP) connections are not supported for WebGL builds; the Photon Cloud exposes WS (9090/9091/9093) and WSS (19090/19091/19093) ports, plus WSS on 443 for restricted networks; Photon's sibling Quantum docs state the browser rule generically ("Browsers cannot establish direct UDP connections, so WebSockets over TCP are utilized instead"). Treat "Fusion WebGL = WebSocket to the Photon Cloud, relay for any client-server traffic" as INFERRED from these, not as a quoted Fusion statement.

### Cited Findings
- VERIFIED. "direct connections are not supported for WebGL builds" and "if a WebGL build acts as the server, it will always utilize a relay connection". [Source](https://doc.photonengine.com/fusion/v2/fusion-choose)
- VERIFIED. Photon Cloud port table includes: "9090 TCP Client to Master Server (WebSockets)", "9091 TCP Client to Game Server (WebSockets)", "9093 TCP Client to Nameserver (WebSockets)", "19090 TCP Client to Master Server (Secure WebSockets)", "19091 TCP Client to Game Server (Secure WebSockets)", "19093 TCP Client to Nameserver (Secure WebSockets)"; UDP ports are 5055-5058 or 27000-27002 and TCP 4530/4531/4533. [Source](https://doc.photonengine.com/fusion/v2/manual/connection-and-matchmaking/tcp-and-udp-port-numbers)
- VERIFIED. Fusion troubleshooting page: "Different protocols. We are moving towards using WSS for the initial connection and Authentication." Listed potential fixes include "Enable Protocol Fallback", "Use WSS port 443 (industries can use ns.photonindustries.io)", "RunInBackgroud", "WebGL: Play audio". It also notes "Browsers typically do not run JS/WebGL games in inactive tabs." and, for Wireshark: "To capture WebSocket traffic, you may want to explicitly use the Photon specific port ranges: `portrange 9090-9093 or portrange 19090-19093`. ... If the clients run WS on port 80 or WSS on port 443, Wireshark will pick up a lot of other network traffic". [Source](https://doc.photonengine.com/fusion/v2/troubleshooting/analyzing-disconnects)
- VERIFIED (Realtime docs, which Fusion is built on; Fusion 2.1 "requires Realtime 5"): "Most of the networks with restricted internet access still allow a secure connection via Secure WebSockets ... Configure your client to use the protocol WebSocketSecure and set the port to 443 for it." and "Photon clients support using proxies for WebSocket connections. In WebGL, proxy support is defined by the browser and system." [Source](https://doc.photonengine.com/realtime/current/connection-and-authentication/secure-networks); Realtime 5 requirement [Source](https://doc.photonengine.com/fusion/v2/getting-started/sdk-download)
- VERIFIED (Quantum docs, not Fusion): "Browsers cannot establish direct UDP connections, so WebSockets over TCP are utilized instead. However, TCP's reliable and sequenced transfer protocol can negatively impact gameplay for players with poor network connections. To provide the best player experience, it is recommended to also offer the game as a download. A warning that the application is switching to WebSockets may appear in the browser, but this can be safely ignored." [Source](https://doc.photonengine.com/quantum/v3/manual/webgl)
- VERIFIED. Fusion encryption page, on connection types: "`Cloud Connection`: This is the connection between the local peer and the Photon Cloud. It is mandatory, primarily used for matchmaking and can serve as a relay if necessary. All GameModes (except `Single player`) maintain at least this type of connection." "`Direct Connection`: This connection is established between a `Fusion Server` and a `Fusion Client` for direct communication." The recommended encrypted cloud-connection setup is "Set Port to `443`. Set the `Protocol` to `UDP`. Set the `AuthMode` to `Auth Once Wss`. Select the `Datagram Encryption GCM`" and "This covers encryption for the `Shared` mode." [Source](https://doc.photonengine.com/fusion/v2/manual/advanced/encryption)
- VERIFIED. Client/Server connection process: clients try a direct UDP connection to the server's STUN-resolved reflexive address for the first 2/3 of 10 attempts at 500 ms intervals, then fall back to relaying through the Photon Cloud: "The connection attempts interval is fixed at 500ms, and the connection attempts limit is set to 10." "(b) Or the connection can be relayed through the Photon Cloud". [Source](https://doc.photonengine.com/fusion/v2/manual/connection-and-matchmaking/connection-process)
- VERIFIED. WebGL-specific Unity caveats recorded by Photon in the Metaverse WebGL sample: `Task.Delay` does not work on WebGL (use `Task.Yield` loop), `OnAudioFilterRead` is not triggered on WebGL, TextMeshPro material-sharing issue. [Source](https://doc.photonengine.com/fusion/v2/industries-samples/metaverse/fusion-metaverse-webgl). Fusion 2.1.3 release notes also list "Fixed: TaskManager.Delay precision loss on long-running WebGL builds". [Source](https://doc.photonengine.com/fusion/v2/getting-started/release-notes/release-notes-2-1)
- VERIFIED. WebGL is in the Fusion 2 supported-platform list ("Android", "WebGL", desktop, consoles, iOS, VisionOS). [Source](https://doc.photonengine.com/fusion/v2/getting-started/sdk-download)

### Inferences
- INFERRED. In a WebGL build the only path is the (TCP) WebSocket cloud connection; in Shared Mode that is the whole topology (one connection, peer to Photon Cloud), which is exactly why Photon says Shared gives "much better latency than Host / Server" on WebGL. In Client/Server modes a WebGL client cannot open the UDP "Direct Connection" to the game server and would run every packet through the Photon Cloud relay (extra hop, TCP head-of-line blocking), which is the "degraded performance ... often lead to disconnects" the config toggle warns about.
- INFERRED. No region or WSS-specific restriction for WebGL is documented beyond ports; the same regions apply (see Region Reference Mapping in the Multiplay/Gameye pages for server placement).

### Gaps
- UNKNOWN / not found in docs: an explicit Fusion 2 statement of which protocol a WebGL build selects by default (WS vs WSS, port 443 vs 19090-range), and whether "Enable Protocol Fallback" is relevant to WebGL. Not found in the Fusion 2 manual; the Realtime "secure-networks" page is the closest official text.

## Key question 3: What a Dedicated Server deployment concretely requires

### Takeaway
Photon does not host, orchestrate, or sell Fusion game-server capacity: "Photon does not provide servers for hosting a dedicated Fusion server application" and "Photon does NOT offer dedicated game session server orchestration". You must build a headless 64-bit Unity server (Linux is the documented container path), run it on your own or a third-party host (Edgegap, Gameye, PlayFab, GameLift, Multiplay are the ones named), and that server is just a Fusion peer started in `GameMode.Server` that connects to the Photon Cloud with your AppId, a region and a session name. A Public Cloud subscription is enough; Enterprise is not required.

### Cited Findings
- VERIFIED. "The server application is built from the Unity project and runs a full headless Unity build. The Dedicated Server has full and exclusive State Authority over all objects. ... Since dedicated servers are usually hosted on public static IPs there is no need for UDP hole punching or network relays. The downside to dedicated servers is the cost of spinning up complete Unity instances for every game session. Photon does not provide servers for hosting a dedicated Fusion server application. The Dedicated Server runs in the Fusion mode `GameMode.Server` and the clients (players) run as `GameMode.Client`." [Source](https://doc.photonengine.com/fusion/v2/manual/network-topologies)
- VERIFIED. Parts involved: "the Fusion Headless build; the Dedicated Game Session Instance running on the Dedicated Server; the Dedicated Server Machine from your preferred Hosting Provider; the Photon Cloud with the Fusion Cloud Plugin; and, the Clients". "The Photon Server SDK is NOT related to the Dedicated Server topology in Fusion!" [Source](https://doc.photonengine.com/fusion/v2/concepts-and-patterns/dedicated-server-overview)
- VERIFIED. Subscription: "A subscription to the Photon PUBLIC CLOUD is sufficient! A Photon ENTERPRISE CLOUD subscription is only necessary to access the features & services which can only be offered in a dedicated environment." "To run a game in `Server Mode` a dedicated game server is needed as well as a Photon Fusion Cloud subscription." The Photon Cloud handles "connection handling; relay fallback; and, state backup for server migration". [Source](https://doc.photonengine.com/fusion/v2/concepts-and-patterns/dedicated-server-overview)
- VERIFIED. Orchestration: "Photon does NOT offer dedicated game session server orchestration. Orchestration services are usually offered by game session hosting providers themselves". "Popular hosting providers include but are not limited to: Edgegap with the Asteroid sample; Gameye; PlayFab; GameLift. It is of course possible to use custom solutions and standalone docker instances if so desired." [Source](https://doc.photonengine.com/fusion/v2/concepts-and-patterns/dedicated-server-overview). Dedicated pages exist for Multiplay (Unity Game Server Hosting) and Gameye; Docker image sample for containerizing. [Multiplay](https://doc.photonengine.com/fusion/v2/technical-samples/dedicated-server/fusion-dedicated-server-multiplay), [Gameye](https://doc.photonengine.com/fusion/v2/technical-samples/dedicated-server/fusion-dedicated-server-gameye), [Docker](https://doc.photonengine.com/fusion/v2/technical-samples/dedicated-server/fusion-dedicated-server-docker-image)
- VERIFIED. Headless build: "Fusion Headless builds support all 64-bit platforms Unity is able to build towards. To create a headless build, simply: Navigate to the `File > Build Settings...` ... Select the `Target Platform`. Ensure the `Architecture` is set to 64-bit. Click on `Build`." [Source](https://doc.photonengine.com/fusion/v2/concepts-and-patterns/dedicated-server-overview). The sample adds: "Dedicated Server Build: this build target can be found only in Unity 2021.2+ and was designed specifically for this purpose, removing unnecessary files and has a better integration with the terminal." and "If you change the Build Target Platform (from Standalone to Dedicated Server, for example), make sure the FUSION_WEAVER symbols is defined in the Scripting Define Symbols for that specific target. Otherwise, Fusion will not be able to weave your project." [Source](https://doc.photonengine.com/fusion/v2/technical-samples/dedicated-server/fusion-dedicated-server)
- VERIFIED. What a server is: "A `Dedicated Server` is nothing more than a Fusion peer started in `Server Mode`, meaning there is not a local `Player` and it will act as the `State Authortity` over the complete `Game State`." Headless detection = command line contains `-batchmode -nographics`; launch example `.\FusionDedicatedServerSample.exe -batchmode -nographics -logFile output.log -session my-custom-session -region us -lobby my-custom-lobby -port 30001 -Pmap city -Ptype free-for-all`; defaults: session "random GUID", region "Best Region", lobby "ClientServer Lobby", port 27015; "Once started, the Game Server will wait for clients to join, and will automatically shutdown and close when all clients disconnect from the session." [Source](https://doc.photonengine.com/fusion/v2/technical-samples/dedicated-server/fusion-dedicated-server)
- VERIFIED. Registration to Photon Cloud (server side): "1. The server starts the game in Server mode. 2. The server creates a new session using the Photon Cloud. ... 9. The server sends a STUN Request to a STUN Server. 10. The server receives the reflexive address from the STUN Server. 11. The server sends the reflexive address to the Photon Cloud." [Source](https://doc.photonengine.com/fusion/v2/manual/connection-and-matchmaking/connection-process). Three documented ways to bind: fully automatic (OS port + STUN), `Address = NetAddress.Any(27015)` (fixed local port + STUN), or `Address` + `CustomPublicAddress` ("Fusion completely bypasses the use of the STUN Protocol ... intended for scenarios where the hosting service already provides the mapping between Local and Public EndPoints"). [Source](https://doc.photonengine.com/fusion/v2/manual/connection-and-matchmaking/matchmaking)
- VERIFIED. Region is mandatory for the server peer: "Considering that a Fusion Server must be connected to a Photon Cloud Region, selecting the best Region for your Server is mandatory." Region is set through `PhotonAppSettings.Instance.AppSettings.GetCopy()` then `photonSettings.FixedRegion = customRegion.ToLower()` and passed via `CustomPhotonAppSettings`; Multiplay requires binding to `0.0.0.0` plus a port from launch args. "Fusion does not support any kind of integration with Multiplay out of the box". Region mapping table given (US West/East/Central -> US, Europe -> EU, Japan/Korea -> JP, Singapore/Australia/India -> ASIA, South America -> SA, China -> CN). [Source](https://doc.photonengine.com/fusion/v2/technical-samples/dedicated-server/fusion-dedicated-server-multiplay)
- VERIFIED. Docker path: "Set Linux as the Target Platform and x86_64 as Architecture. Check the Server Build flag. Set the executable name to server.x86_64." Run with `docker run -d -p 27015:27015/udp fusion-dedicatedserver -s my_session -r eu -l my_lobby`; args `-i` custom public IP and `-p` custom public port, "Default: Empty, the Server will use the STUN Service to discover its Public IP." Docker image sample version 1.0.2 (Nov 20, 2024). [Source](https://doc.photonengine.com/fusion/v2/technical-samples/dedicated-server/fusion-dedicated-server-docker-image)
- VERIFIED. Gameye spawn = HTTP POST to `https://api.gameye.io/session` with args `-s <game session name>`, `-r <photon region>`; Gameye-to-Photon region mapping provided (eu-west/eu-south -> eu, na-east/na-central -> us, na-west -> usw, sa-east -> sa, asia-east -> asia, asia-northeast and oce-east -> jp). [Source](https://doc.photonengine.com/fusion/v2/technical-samples/dedicated-server/fusion-dedicated-server-gameye)
- VERIFIED. Dedicated server sample version is 2.0.6 (Jul 10, 2025), i.e. the sample predates 2.1; the Host Migration sample is at 2.1.2 (Sep 08, 2026) and Projectiles Essentials at 2.1.1 (Jul 10, 2026). [Sample](https://doc.photonengine.com/fusion/v2/technical-samples/dedicated-server/fusion-dedicated-server)
- VERIFIED. Dashboard-level helpers for server deployments: `FusionSessionCreationControlEnable` + `FusionSessionCreationControlServerId` ("especially useful for blocking all peers except the server peer from creating new sessions"), and `FusionDummyTrafficEnable` ("especially for Fusion Client/Server modes where the Photon Cloud (relayed) connection is not being actively used, as clients are connected directly to the Fusion Server peer"). ## Key question 6: Prediction, interpolation delay, input delay and lag compensation; what this means for skillshots

### Takeaway
Server/Host mode: the local player's input-authority objects are predicted (client runs ahead of the server, rolls back and resimulates on each snapshot), all other objects are "proxies" rendered by snapshot interpolation at an adaptive, jitter-derived delay behind the server; server-side lag compensation rewinds hitboxes by "the sum of the client's prediction and its interpolation delay" (sub-tick optional) and exists only in Server/Host. Shared mode: no prediction, no resimulation, no lag compensation; the owner applies input immediately and decides its own hits locally, remote objects are interpolated. For a MOBA skillshot (projectile with travel time) this means: Server mode gives a cheat-resistant WYSIWYG hit model with a spawn-delay problem that Photon solves with projectile data buffers (no NetworkObject per projectile); Shared mode gives zero-latency local casting and client-decided hits with no server referee.

### Cited Findings
- VERIFIED. Prediction definition: "To achieve both goals, the client needs to send ahead of time, which it can do by positioning itself ahead of the server on the timeline. This is prediction." "Normally, the number of predicted ticks grows with ping, but Fusion clients can be configured to let some network lag through, enough to reduce or completely cap the number of predicted ticks. This is input delay." "Input delay is only supported in Server Mode and Host Mode." [Source](https://doc.photonengine.com/fusion/v2/manual/advanced/time-synchronization)
- VERIFIED. Interpolation delay: "Since the server simulates all objects, the client can get away with predicting just a small number of them, like just the local player's avatar. The client can render any other object simply by interpolating the snapshots it has ... the client needs to delay its snapshot \"playback time\" enough that it nearly always has a pair of snapshots that can produce that moment in time. This is interpolation delay." The amount is adaptive: "Max Late Snapshots: The client will delay snapshot interpolation long enough to cover all but this percent of packet jitter." plus "Redundant Snapshots" multiplier and "State Receive Buffer Delay Added" (ms or ticks). [Source](https://doc.photonengine.com/fusion/v2/manual/advanced/time-synchronization)
- VERIFIED. Release note (build 1627): "Change DEFAULT_MAX_LATE_INPUTS_PERCENTILE from 5 to 1. This is slightly less conservative and will move client time closer to server time at the cost of a slightly greater risk of an input drop" and "Expose TimeSyncConfiguration in NetworkProjectConfig in the Unity inspector. We continue to recommend you use the defaults". Shared Mode can override time sync via `NetworkProjectConfig.TimeSynchronizationOverride` (build 1513). [Source](https://doc.photonengine.com/fusion/v2/getting-started/release-notes/release-notes-2-1)
- VERIFIED. Remote render time is behind the latest server tick: "Remote Render Time = values interpolated between remote interpolation ticks (there needs to be a safety window before latest server tick is used for interpolation, therefore remote interpolation ticks are a little bit more in the past than latest server tick)". Local vs remote time frames: "All objects on the Host/Server are always simulated and rendered in the Local time frame. Clients are rendering objects in both time frames, usually Local is used for local objects and Remote is used for remote objects. For simulation, clients are usually only simulating their local objects (= `FixedUpdateNetwork` is not executed for proxies)". Rendering rule used by Photon: `float renderTime = Object.IsProxy ? Runner.RemoteRenderTime : Runner.LocalRenderTime;`. [Source](https://doc.photonengine.com/fusion/v2/technical-samples/projectiles-essentials)
- VERIFIED. Server-side lag compensation: "Lag Compensation is only available in Server Mode and Host Mode." "Fusion keeps a history of where hitboxes were previously located and knows how far behind each client's view is compared to the current server state. Using this history, Fusion is able to compensate for lag by raycasting in the past." "The amount of lag that the server needs to compensate ... is the sum of the client's prediction and its interpolation delay." Sub-tick accuracy via `HitOptions.SubtickAccuracy`; queries: raycast, sphere overlap, box overlap, `IgnoreInputAuthority`, `IncludePhysX` (regular colliders are "not lag-compensated"); limits: 31 Hitbox nodes per HitboxRoot, 3D shapes only (box/sphere) but usable in a locked plane for 2D/top-down; config: `Hitbox Buffer Length In Ms`, `Hitbox Default Capacity` (min 16). Trade-off stated: "the target may be hit even if they felt they were already safely tucked away behind a wall." [Lag comp](https://doc.photonengine.com/fusion/v2/manual/advanced/lag-compensation), [Time sync](https://doc.photonengine.com/fusion/v2/manual/advanced/time-synchronization)
- VERIFIED. Shared Mode: "In Shared Mode, the client who has InputAuthority is also the StateAuthority. Because of this, inputs do not need to be sent to a remote authority, and no complex prediction or re-simulation logic is required." [Source](https://doc.photonengine.com/fusion/v2/manual/input/shared-mode-input). "Shared Mode is also the only mode that does not need to run resimulations". [Source](https://doc.photonengine.com/fusion/v2/fusion-choose). "It is not required for Shared Mode because each client performs their own hitbox detection locally." [Source](https://doc.photonengine.com/fusion/v2/manual/network-project-config)
- VERIFIED. Server-mode input pipeline: "Inputs are consumed in FixedUpdateNetwork on the: InputAuthority: To simulate local movement immediately (Prediction). StateAuthority: To process the authoritative move ... InputAuthority (again): To re-simulate frames". "GetInput returns true only for the InputAuthority and StateAuthority. All other clients (proxies) receive false." Inputs must be sanitized on the server ("we can't trust data from clients"). Latency-reduction techniques: Render Prediction ("can reduce system latency from ~12ms down to ~4ms"), input smoothing, `IBeforeUpdate`. [Source](https://doc.photonengine.com/fusion/v2/manual/input/player-input)
- VERIFIED. Spawn is not predicted in Server/Host: "Since NetworkObject spawn is not predicted in Fusion 2, all projectiles are spawned by the State Authority. There will be a significant pause after fire input before the projectile is actually fired when network conditions are not ideal." Photon's recommended approaches: (C) projectile count property, "Suitable only for hitscan projectiles ... Good solution for simplistic use cases ... e.g. top down shooter with simple projectiles and short projectile visuals (trails)"; (D) Projectile Data Buffer (ring buffer of `INetworkStruct` in a NetworkBehaviour, projectile is "just a visual"), "recommended for most games", with a Kinematic variant (`FireTick`, `FirePosition`, `FireVelocity`, `HitPosition`, `FinishTick`) for travelling projectiles; kinematic collision uses `Runner.LagCompensation.Raycast(previousPosition, direction, ..., Object.InputAuthority, ..., HitOptions.IncludePhysX | HitOptions.IgnoreInputAuthority)` per tick. "Projectiles Advanced is not yet available for Fusion 2" (overview page) while a Projectiles Advanced 2.x page exists with 8 weapons; treat Advanced as partially available. [Essentials](https://doc.photonengine.com/fusion/v2/technical-samples/projectiles-essentials), [Advanced](https://doc.photonengine.com/fusion/v2/technical-samples/projectiles-advanced/overview)
- VERIFIED. Forecast Physics (2.1) "is available in Host, Server and Shared Mode" and "uses extrapolation to place physics objects in the local time of all players". [Source](https://doc.photonengine.com/fusion/v2/getting-started/release-notes/whats-new-2-1)
- VERIFIED. Interpolation internals: `TryGetSnapshotsBuffers()` returns from/to buffers and alpha; `NetworkBehaviourBufferInterpolator`; `ChangeDetector` sources `SimulationState`, `SnapshotFrom`, `SnapshotTo`. 2.1: "OnChangedRender now called at alpha = 0.5 to match interpolators (and reduce perceived latency)"; `NetworkObject.EnableInterpolation` (default true) can be disabled per object; `NetworkObject.ResetToLatestState()`; `ClientsOnlyRollbackUpdatedObjects` (2.1.3) to skip resimulating untouched objects. [Buffers](https://doc.photonengine.com/fusion/v2/manual/advanced/network-buffers), [Release notes](https://doc.photonengine.com/fusion/v2/getting-started/release-notes/release-notes-2-1)

### Inferences
- INFERRED. Skillshot in Server Mode: cast feedback is immediate on the caster (predicted FUN + local visual via the data-buffer approach), the projectile's per-tick raycast runs on the server (and predictively on the caster) with lag compensation keyed to `Object.InputAuthority`, so "what the caster saw" is honoured within the hitbox buffer window. Targets see the projectile in Remote Render Time, i.e. late by roughly one-way latency plus interpolation delay; dodges therefore resolve against the caster's view, the classic "hit behind the wall" trade-off Photon states. Hitscan (count property) is the cheapest, kinematic buffer is the recommended general case.
- INFERRED. Skillshot in Shared Mode: the caster owns the projectile state and decides hits locally (perfectly WYSIWYG for the caster, no server referee), then requests damage via RPC to the target's StateAuthority; the target can only accept/reject on its own client logic. Latency felt by the target = one-way cloud latency + interpolation delay, same as Server mode, but there is no lag compensation primitive at all, so any "fairness" logic (e.g. rewinding the target's position) must be hand-written and runs on an untrusted client.
- INFERRED. Nothing in the docs gives a fixed "N ms behind" for proxies; it is a jitter-percentile buffer, so on TCP WebSocket (WebGL) jitter spikes will push interpolation delay up more than on UDP.

### Gaps
- UNKNOWN / not found in docs: numeric defaults for Max Late Snapshots / Redundant Snapshots / Delay Added (the config page lists the fields without their default values; only the inputs percentile default change 5 -> 1 is stated in release notes).
- UNKNOWN: default Client/Server tick rate value in 2.1 is not stated on the pages read (only the allowed range 8..256 and the Shared cap of 32); see KQ11.

## Key question 7: Reconnection and host migration behaviour (Server mode vs Shared mode)

### Takeaway
Server/Host mode: a reconnecting client can get its previous PlayerRef back via `StartGameArgs.PlayerUniqueId` (2.1, works in Shared too) or be re-mapped to its old object via `ConnectionToken` + `GetPlayerConnectionToken` (server/host only); the server itself survives Photon Cloud loss (quick re-join, then move-to-new-room). Host Migration exists only for Host mode (snapshot to cloud every N seconds, 30 s recommended; state since last snapshot is lost). Shared mode: no host migration (master client role just moves), the Cloud Connection Lost feature is "not supported", and a leaver's objects are destroyed unless `Destroy When State Authority Leaves` is unchecked, in which case they stay with StateAuthority `PlayerRef.None` and a rejoiner can `RequestStateAuthority` on them.

- VERIFIED. Cloud connection lost (2.0.5+, 2.1): up to five automatic reconnect attempts; callback `NetworkRunner.CloudConnectionLost(runner, reason, reconnecting)`; modes `Disabled`, `QuickRejoin`, `MoveSessionToNewRoom` (2.1 default for servers); "This feature applies only to Client/Server Modes (Host, Server, and Client). - VERIFIED. PlayerUniqueId (2.1): "you can pass an ID via the StartGameArgs.PlayerUniqueId (long) when connecting to a session (supports both Shared and Client-Server Modes). This allows players to connect to the session using a consistent PlayerRef. ... Release note: "StartGameArgs.PlayerUniqueId enables reconnects to maintain the same PlayerRef". - VERIFIED. Shared mode: "Host Migration also does not occur in Shared Mode because there is technically no Player Host; instead, the SharedModeMasterClient is transferred to another player if they disconnect, so Host Migration becomes unnecessary." - VERIFIED. Orphan handling: "If a NetworkObject has Allow State Authority Override checked and Destroy When State Authority Leaves unchecked ... the NetworkObject will not be destroyed if the player disconnects; however, the SharedModeMasterClient can despawn this object despite not having StateAuthority over it." [Source](https://doc.photonengine.com/fusion/v2/manual/shared-mode-master-client)

### Inferences
- INFERRED. In Server Mode the recommended reconnection design for a 3v3 MOBA is: stable `PlayerUniqueId` per account (same PlayerRef on rejoin) + server-side map from PlayerRef/UserId to the hero object + a timeout before the hero is removed; the hero object itself keeps existing on the server during the drop because the server holds all state. ## Key question 9: Is a WebGL CLIENT connecting to a non-WebGL dedicated Linux server officially supported?

### Takeaway
Technically possible but officially "not recommended and by default disabled": Client/Server GameModes in WebGL builds are gated behind `Allow Client Server Modes in WebGL` / "Enable ClientServer Modes in WebGL builds" with an explicit warning of degraded performance and disconnects. No Photon sample demonstrates a WebGL client on a dedicated server; both official WebGL samples are Shared Mode.

### Cited Findings
- VERIFIED. "Server and Host mode are not recommended and by default disabled." "To enable Server / Host Mode on WebGL toggle \"Enable ClientServer Modes in WebGL builds\" in the `NetworkProjectConfig` to true." [Source](https://doc.photonengine.com/fusion/v2/fusion-choose)
- VERIFIED. "Allow Client Server Modes in WebGL: By default, when using Client Server Mode, WebGL builds are disabled. They are not recommended since they can lead to degraded performance and Client Host are not reliable and often lead to disconnects in WebGL. If checked, this setting will allow Client Servers to be utilized despite these limitations." [Source](https://doc.photonengine.com/fusion/v2/manual/network-project-config)
- VERIFIED. "direct connections are not supported for WebGL builds" [Source](https://doc.photonengine.com/fusion/v2/fusion-choose); the Client/Server path otherwise expects a direct UDP socket with relay fallback via the Photon Cloud. [Source](https://doc.photonengine.com/fusion/v2/manual/connection-and-matchmaking/connection-process)
- VERIFIED. "Fusion Headless builds support all 64-bit platforms Unity is able to build towards." (so the Linux server side is supported regardless of client platform). [Source](https://doc.photonengine.com/fusion/v2/concepts-and-patterns/dedicated-server-overview)
- VERIFIED. Both WebGL samples (Crazy Starter WebGL, Metaverse WebGL) are Shared Mode; the dedicated server sample lists no WebGL client. [WebGL sample](https://doc.photonengine.com/fusion/v2/technical-samples/fusion-webgl), [Dedicated sample](https://doc.photonengine.com/fusion/v2/technical-samples/dedicated-server/fusion-dedicated-server)

### Inferences
- INFERRED. A WebGL client in `GameMode.Client` would reach the Linux server only through the Photon Cloud relay over WebSocket; the dedicated server's advantage of "no need for UDP hole punching or network relays" is lost for those clients, and the relay traffic counts against Photon traffic allowances. A mixed audience (native mobile app on UDP direct, browser on relay) would see asymmetric latency.

### Gaps
- UNKNOWN / not found in docs: any explicit "supported / unsupported" sentence for the specific pairing WebGL client + native server; the docs only speak of "WebGL builds" in "Client Server Mode" generically. Not found in docs.

## Key question 10: Unity Dedicated Server build target (Unity 6) and why it suits a Fusion server build

### Takeaway
Unity 6's Dedicated Server target is a sub-target of Linux/macOS/Windows that strips GPU-only assets, disables audio, lighting threads, rendering/UI/input player-loop callbacks, and never initializes a graphics device; it is "similar to the desktop headless mode" (`-batchmode -nographics`) but with those optimizations. Photon's dedicated-server sample explicitly recommends it over a Standalone build.

### Cited Findings
- VERIFIED. "The Dedicated Server build target is a sub-target of the three Desktop Platforms (Linux, macOS, and Windows) that's optimized for running as a dedicated server. Using Dedicated Server build target, you can cut back on your server builds' CPU, memory, and disk space requirements." "Most of the optimizations take place through stripping code and assets that aren't necessary for a server build." [Source](https://docs.unity3d.com/6000.0/Documentation/Manual/dedicated-server-introduction.html)
- VERIFIED. Automatic optimizations: "Deactivates the Audio Subsystem; Removes lighting threads; Removes some Player loop callbacks; Removes GPU-only assets". Removed callbacks include `SendMouseEvents`, `UpdateAllRenderers`, `PlayerUpdateCanvases`, all audio, all UI (`UIElementsUpdatePanels`), all input (`UpdateInputManager`). "Because the Dedicated Server build target doesn't initialize a graphics device, there's no need to include this data." Preserved: CPU Read/Write-enabled textures/meshes, Resources, "Mesh data that internal systems that run on the CPU require (such as physics)". Optional "Enable Dedicated Server Optimizations" additionally strips Shaders and Fonts. Limitation: "Dedicated server optimizations don't apply to content built with the Scriptable Build Pipeline (SBP) ... Addressables system and Entities subscenes". [Source](https://docs.unity3d.com/6000.0/Documentation/Manual/dedicated-server-optimizations.html)
- VERIFIED. Headless vs Dedicated Server: "The Dedicated Server build target is similar to the desktop headless mode. The only difference is that the Dedicated Server build target is optimized to increase memory and CPU performance when running as a networked application. Desktop headless mode allows you to run applications in batchmode on any desktop platform without initializing the graphics device ... by passing the `-batchmode` and `-nographics` command line arguments". [Source](https://docs.unity3d.com/6000.0/Documentation/Manual/desktop-headless-mode.html)
- VERIFIED. Install: "Select the Dedicated Server build support module for your target platform. For example, select Linux Dedicated Server Build Support". [Source](https://docs.unity3d.com/6000.0/Documentation/Manual/dedicated-server-requirements.html)
- VERIFIED. Photon on build target choice: Standalone build "will contain all game assets and ... will run in the background (forcing it to close require killing the process)"; Dedicated Server target "removing unnecessary files and has a better integration with the terminal"; FUSION_WEAVER define must be present for that target. Headless detection in the sample is "-batchmode -nographics" on the command line. [Source](https://doc.photonengine.com/fusion/v2/technical-samples/dedicated-server/fusion-dedicated-server)
- VERIFIED. Fusion option to skip `Render()` in batch mode: `Invoke Render In Batch Mode` / `NetworkProjectConfig.InvokeRenderMode`. [Source](https://doc.photonengine.com/fusion/v2/manual/network-project-config)

### Inferences
- INFERRED. Because the Dedicated Server target removes all input callbacks, a Fusion server build must not rely on Unity Input in FUN (it does not: the server consumes `GetInput()` from clients), and because UI callbacks are removed, any `com.unity.ugui`-based Fusion menu/stats should be excluded (2.1.3 made ugui optional).
- INFERRED. Physics still works server-side (mesh data needed by physics is preserved), which is what hitbox/lag-compensation and kinematic projectile raycasts rely on.

### Gaps
- The Unity 6.0 manual was read; the 6000.6-specific manual was not checked (same page set is expected but UNVERIFIED for that version).

## Key question 11: Bandwidth and tick-rate defaults

### Takeaway
Shared Mode: default 32 Hz tick / 16 Hz send, hard cap 32 (configurable below since 2.1, overridable from dashboard/webhooks). Client/Server: any tick rate 8..256 Hz with send interval 1..8 that divides evenly; the default value is not stated on the pages read. Photon traffic allowance is 3 GB per peak CCU per month with a 500 messages/s/room fair-use guideline; Server-mode traffic between clients and your server does not transit Photon unless relayed.

### Cited Findings
- VERIFIED. "In Shared Mode specifically, Fusion 2 locked the tick rate to 32hz and the send rate to 16hz. In Fusion 2.1 both rates remain subject to a cap of 32hz, but can be adjusted freely below this limit." "Fusion 2.1 greatly expands this to allow any tick rate between 8hz and 256hz, and any send rate down to 1/8 the tick rate as long as it divides evenly." [Source](https://doc.photonengine.com/fusion/v2/getting-started/release-notes/whats-new-2-1); "The default tick rate of 32 and send rate of 16 remains the same" (Shared). [Source](https://doc.photonengine.com/fusion/v2/getting-started/release-notes/release-notes-2-1)
- VERIFIED. Config semantics: "Client Send Rate: ... represented by an interval in the 1-8 range. A value of 1 means data is sent every tick, 2 means it's sent every second tick"; "Server Send Rate ... same options and restrictions"; `Replication Features` default "Scheduling" (per-tick data limit culling with priority bump); `Input Transfer Mode` Redundancy (default, delta-compressed redundant input) vs Latest State; Player Count 1..255 (Shared clamps 1..2048 per release notes). [Source](https://doc.photonengine.com/fusion/v2/manual/network-project-config)
- VERIFIED. Object Send Priority (2.1) reduces per-object send rate (priority 2 = SendRate/2, etc.); in Shared each client controls the rate of objects it receives (`SetPriority` with `LocalPlayer` only); on Host/Server the server sets it per player-object pair; 2.1.2 adds server max-packets-per-send limits (`GameChannelSendCount`, `GameReliableChannelSendCount`). [What's new](https://doc.photonengine.com/fusion/v2/getting-started/release-notes/whats-new-2-1), [Release notes](https://doc.photonengine.com/fusion/v2/getting-started/release-notes/release-notes-2-1)
- VERIFIED. "All incoming and outgoing messages to the Photon Cloud servers count toward your traffic allowance. Every plan includes 3 GB per peak CCU per month". "Photon recommends staying below 500 messages per second per room, a fair-use guideline rather than a hard limit". [Source](https://doc.photonengine.com/photon/current/pricing)
- VERIFIED. "When using Shared Mode or Host mode with a relay server, bandwidth use becomes more of a factor to keep in mind although a well optimized Fusion game should not reach the free bandwidth limit. When using Server Mode, bandwidth pricing will depend more on the third party server provider." [Source](https://doc.photonengine.com/fusion/v2/fusion-choose)
- VERIFIED. Shared-mode AOI cell size is configurable in 2.1 (was fixed at 32 units). [Source](https://doc.photonengine.com/fusion/v2/getting-started/release-notes/whats-new-2-1)

### Inferences
- INFERRED. On WebGL + Shared, every packet is cloud traffic (counts toward the 3 GB/CCU/month), and the 32 Hz cap bounds the simulation granularity available to a browser MOBA; Server mode could run a higher tick rate but a WebGL client would still route through the cloud relay.

### Gaps
- UNKNOWN: the numeric default Client/Server tick rate and send interval in 2.1.x (not printed on the config or release-notes pages read; verify in the project's NetworkProjectConfig asset).
