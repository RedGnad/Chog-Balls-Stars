# Diagnosing stutter in a Unity 6 Web (WebGL) build on a low-end Android phone (Chrome)

Scope: Unity 6000.6.x, Web platform (IL2CPP + Emscripten + WebAssembly, WebGL 2), Chrome on Android, phone reported as "Redmi 11C". Research date: 2026-10-08. Every claim carries a tag: VERIFIED (read on the cited page in this pass), VERIFIED-EXCERPT (quoted from a search-engine excerpt of the cited page, page not re-read in full), INFERRED (my reasoning from cited facts), UNKNOWN / NOT FOUND (no source found). Manual URLs are the 6000.6 pages unless stated; the same pages exist under /6000.3/ (LTS) with the same slugs.

Legend of URL patterns that returned HTTP 404 in this pass (do not cite them): `Manual/webgl-browser-compatibility.html`, `Manual/webgl-mobile.html`, `Manual/frame-timing-manager-get-data.html`. The live slugs are `webgl-browsercompatibility.html`, `web-optimization-mobile.html`, and the `FrameTimingManager` ScriptReference page.

## Key question 1: Official Unity 6 tooling and procedure to profile a Web build running on an Android phone

### Takeaway
Unity 6.6 documents a dedicated Web profiling workflow: Development Build, then either Autoconnect via the Build-and-Run local server (same machine only) or, for a phone, "Enable Web Profiling" in the Profiler window, which displays an IP:port that you paste into the build's on-screen "Profile" button (Default/PWA templates only) or pass as `--player-connection-ip` in `index.html`. Profiling is development-builds only; the Frame Debugger does not work on Web; FrameTimingManager works on Web but reports no GPU time; `Recorder` and `Profiler.GetTotalAllocatedMemoryLong` need a Development Player; the Diagnostics Overlay works in Release builds and shows FPS and both JS and WASM heaps on the phone without any PC.

### Cited Findings
- VERIFIED. "Profiling is only available for development builds." Basic draw call data can be profiled but "the Frame Debugger doesn't work on the Web platform." [Unity 6.6 Manual: Profile a Web build](https://docs.unity3d.com/6000.6/Documentation/Manual/web-profile.html)
- VERIFIED. Method 1 (same machine): File > Build Profiles > Web > enable Development Build and Autoconnect Profiler > Build and Run. Unity starts a temporary local server, opens the build in the browser, and the build connects and starts profiling automatically; "Stop Profiling" in the running build disconnects. [Profile a Web build](https://docs.unity3d.com/6000.6/Documentation/Manual/web-profile.html)
- VERIFIED. Method 2 (another device, i.e. the phone): build with Development Build; in the Editor open Window > Analysis > Profiler, select Play Mode > "Enable Web Profiling"; a window shows that web profiling is active and displays an IP address and port; run the build on the device, press "Profile" in the running build, paste the IP:port when prompted; data appears in the Profiler window in real time. [Profile a Web build](https://docs.unity3d.com/6000.6/Documentation/Manual/web-profile.html)
- VERIFIED. "Autoconnect works automatically only on the same device as the Editor." To capture startup data on another device, open the build's `index.html`, find the `var config` block with `arguments: []`, and set `"--player-connection-ip=xxxxxx"` with the copied IP and port. [Profile a Web build](https://docs.unity3d.com/6000.6/Documentation/Manual/web-profile.html)
- VERIFIED. The on-screen "Profile" button is included only in the Default and PWA Web templates; a custom template must add `profiler.js` and `unityProfiler.createButton(unityInstance)` inside `#if DEVELOPMENT_PLAYER` blocks, and call `unityProfiler.shutDown()` on quit. [Profile a Web build](https://docs.unity3d.com/6000.6/Documentation/Manual/web-profile.html)
- VERIFIED. To collect data while the browser window is inactive, enable Run In Background in Player Settings. [Profile a Web build](https://docs.unity3d.com/6000.6/Documentation/Manual/web-profile.html)
- VERIFIED. The generic target-device page says only: "Profiling on the Web platform has a different workflow" and links to the page above; it gives no port numbers, firewall or WebSocket details. [Collect performance data on a target platform](https://docs.unity3d.com/6000.6/Documentation/Manual/profiling-target-device.html)
- VERIFIED. Autoconnect Profiler: "Enable this setting to automatically connect to the Profiler when your application starts"; the Editor's IP address is embedded in the player at build time. Deep Profiling Support "adds a small amount of overhead to your build". [Build Profiles Profiler settings](https://docs.unity3d.com/6000.6/Documentation/Manual/profiler-build-settings-reference.html)
- VERIFIED. Web build settings reference: Development Build "Builds the Player in development mode, which by default includes the Profiler and assertions in your managed assemblies"; Autoconnect Profiler is only available when Development Build is selected; Deep Profiling "might slow script execution". [Web build settings reference](https://docs.unity3d.com/6000.6/Documentation/Manual/web-build-settings.html)
- VERIFIED. Unity Web has no source-level debugging: "Visual Studio doesn't support debugging Unity Web content"; diagnosis relies on browser console output, development builds, symbol files, stack-trace mapping. [Debug and troubleshoot Web builds](https://docs.unity3d.com/6000.6/Documentation/Manual/webgl-debugging.html)
- VERIFIED. `Profiler.enabled` "Enables the Profiler." With `Profiler.enableBinaryLog` the player saves profiling data to `Profiler.logFile` (extension `.raw`), loadable in the Editor's Profiler window; on WebGL the doc's example notes the file lands at a path like `/idbfs/some-hash/profiler.raw`. The page has no statement about release builds or platform support. [ScriptReference: Profiler.enabled](https://docs.unity3d.com/6000.6/Documentation/ScriptReference/Profiling.Profiler-enabled.html)
- VERIFIED. `Profiler.GetTotalAllocatedMemoryLong`: "The total memory allocated by the internal allocators in Unity" (includes a CPU copy of each texture). "This returns 0 if the Profiler is not available." [ScriptReference: Profiler.GetTotalAllocatedMemoryLong](https://docs.unity3d.com/6000.6/Documentation/ScriptReference/Profiling.Profiler.GetTotalAllocatedMemoryLong.html)
- VERIFIED. `UnityEngine.Profiling.Recorder` "Records profiling data produced by a specific Sampler"; `elapsedNanoseconds` = accumulated Begin/End time for the previous frame; `sampleBlockCount` = number of Begin/End pairs; it collects data "regardless of the Profiler state", but Samplers are available only in the Editor and Development Players; check `isValid`. [ScriptReference: Profiling.Recorder](https://docs.unity3d.com/6000.6/Documentation/ScriptReference/Profiling.Recorder.html)
- VERIFIED. FrameTimingManager: lower overhead than the Profiler, meant for Players, used to decide whether CPU or GPU limits the framerate. Always active in Development Player builds; in release Players enable "Frame Timing Stats" (Edit > Project Settings > Player), or attach a `ProfilerRecorder`, which enables it automatically. Results arrive with a fixed four-frame delay; missing GPU timings are reported as zero. Platform exceptions: "WebGL provides no GPU time." [ScriptReference: FrameTimingManager](https://docs.unity3d.com/6000.6/Documentation/ScriptReference/FrameTimingManager.html)
- VERIFIED. The manual's support table lists WebGL as "Partial: GPU Frame Time measurement is unsupported." [Frame timing manager introduction](https://docs.unity3d.com/6000.6/Documentation/Manual/frame-timing-manager.html)
- VERIFIED. `FrameTiming` fields: `cpuFrameTime` ("total CPU frame time calculated as the time between ends of two frames ... includes all waiting time and overheads, in ms"), `cpuMainThreadFrameTime` ("Total time between start of the frame and when the main thread finished the job, in ms"), `cpuMainThreadPresentWaitTime`, `cpuRenderThreadFrameTime`, `gpuFrameTime`, `frameStartTimestamp`, `firstSubmitTimestamp`, `cpuTimePresentCalled`, `cpuTimeFrameComplete`, `heightScale`, `widthScale`, `syncInterval`. [ScriptReference: FrameTiming](https://docs.unity3d.com/6000.6/Documentation/ScriptReference/FrameTiming.html)
- VERIFIED. `Time.unscaledDeltaTime`: "The timeScale-independent interval in seconds from the last frame to the current one (Read Only)"; "On Android platforms, Time.unscaledDeltaTime may return very small values on the first frame" and after resuming from pause. [ScriptReference: Time.unscaledDeltaTime](https://docs.unity3d.com/6000.6/Documentation/ScriptReference/Time-unscaledDeltaTime.html)
- VERIFIED. Web Player settings has "Show Diagnostics Overlay" under Publishing Settings; "On a mobile device, the Diagnostics icon appears on the bottom-right of the screen"; the JS-memory metric relies on `performance.memory`, which "isn't supported on iOS devices." [Web Player settings](https://docs.unity3d.com/6000.6/Documentation/Manual/class-PlayerSettingsWebGL.html)
- VERIFIED-EXCERPT. The overlay is "available for both Development and Release builds" and reports JavaScript heap figures, WASM heap figures, time from page load to first frame, an average FPS over 10 seconds, and the number of rendered frames that took unusually long compared to their previous frames. [Web Player settings (6000.0 page, excerpt)](https://docs.unity3d.com/6000.0/Documentation/Manual/class-PlayerSettingsWebGL.html)
- VERIFIED. Unity staff (jamess_unity, 21 Oct 2024): "We have included tools (Web Diagnostics Overlay) to make it easy to see how much memory the game is using in the browser." [Unity Discussions: Unity 6 updates for platforms](https://discussions.unity.com/t/unity-6-updates-for-platforms/1529798)
- VERIFIED. For performance testing on mobile the manual says to disable Development Build and set Code Optimization to "Disk Size with LTO" ("Use this setting for final releases or performance testing only" because LTO builds take long). [Optimize Web platform for mobile](https://docs.unity3d.com/6000.6/Documentation/Manual/web-optimization-mobile.html)

### Inferences
- INFERRED. Two builds are needed, not one: a Development Build (Profiler, `Recorder`, `GetTotalAllocatedMemoryLong`, Profile button) to attribute time to systems, and a Release build (Disk Size with LTO, Exceptions None, Frame Timing Stats on, Diagnostics Overlay on) to measure the real frame-time distribution. The docs explicitly say a Development Build is not what you performance-test on mobile, and `GetTotalAllocatedMemoryLong` returns 0 without the Profiler.
- INFERRED. The phone and the Editor must be on the same LAN (the build pastes the Editor's IP:port). The manual never names the transport (WebSocket or otherwise) nor a firewall rule; if the connection fails, open the Editor's listening port on the host firewall and retry. Tagged UNKNOWN below.
- INFERRED. On WebGL, `FrameTimingManager` still gives `cpuFrameTime`, `cpuMainThreadFrameTime`, `cpuRenderThreadFrameTime` and `cpuMainThreadPresentWaitTime`; only `gpuFrameTime` is 0. A GPU-bound frame therefore shows up indirectly as a large `cpuMainThreadPresentWaitTime` or as a frame time that collapses when resolution is halved (see protocol in Key question 7), not as a GPU number.
- INFERRED. `Profiler.enabled` + `enableBinaryLog` on WebGL writes to IDBFS inside the browser's IndexedDB; retrieving `profiler.raw` from the phone requires JS-side IndexedDB access or a download plugin. The live Profiler connection is the practical route.

- UNKNOWN. Whether the Web Profiler connection uses WebSocket: the 6000.6 pages never say. Treat "WebSocket" as unverified.
- UNKNOWN. Quantified overhead of a Development Build or Deep Profiling on Web: the docs say "small amount of overhead" and "might slow script execution", no numbers.
- UNKNOWN. Whether `Profiler.GetMonoUsedSizeLong` / `GetTotalReservedMemoryLong` return non-zero in a Release Web build: not stated; the sibling page says 0 "if the Profiler is not available."

## Key question 2: Chrome Android remote debugging, Performance panel, and JS-side probes

### Takeaway
chrome://inspect/#devices over USB opens a full DevTools instance against the phone's tab, and its Performance panel records the phone's own main thread, Frames and GPU tracks; CPU throttling is a desktop-simulation feature and is not needed when recording on the real device. `performance.memory` is Chromium-only and deprecated, `measureUserAgentSpecificMemory` needs cross-origin isolation, `WEBGL_debug_renderer_info` returns the GPU renderer string (the fastest way to tell a Mali-G52 phone from an Adreno 610 phone), and the Compute Pressure API exposes only a "cpu" source today, no thermals.

### Cited Findings
- VERIFIED. Procedure: on the phone enable Developer Options > USB Debugging; on the desktop open `chrome://inspect#devices`, enable "Discover USB devices", connect by USB, accept the debugging prompt on the phone; the device model appears; under it, enter a URL in "Open tab with url" or click "Inspect" next to an open tab to get a DevTools instance. "The DevTools version matches the Chrome version on the device." Manual alternative: `adb forward tcp:9222 localabstract:chrome_devtools_remote`, then `http://localhost:9222/json`. [Chrome DevTools: Remote debug Android devices](https://developer.chrome.com/docs/devtools/remote-debugging)
- VERIFIED. Performance panel: Record, interact, Stop; the "Main" section is a flame chart of main-thread activity; the "Frames" section shows per-frame FPS; red bars in the FPS chart mean "the framerate dropped so low that it's probably harming the user experience"; a red triangle on a Task marks a long task; a CPU chart full of colour means the CPU was maxed out. CPU throttling: "4x slowdown" and, for low-end mobile, "20x slowdown". [Chrome DevTools: Analyze runtime performance](https://developer.chrome.com/docs/devtools/performance)
- VERIFIED. Performance panel reference (updated 2025-04-03): Frames track colours are idle (white), rendered on time (green), partially presented (yellow), dropped (red: "Chrome can't render the frame in reasonable time"); "View GPU activity in the GPU section"; "Use the Main track to view activity that occurred on the page's main thread"; Capture settings let you "calibrate custom CPU throttling presets" to match low/mid-tier mobile, but "DevTools can't truly simulate mobile CPU architectures"; the Memory checkbox adds a JS Heap chart. [Chrome DevTools: Performance reference](https://developer.chrome.com/docs/devtools/performance/reference)
- VERIFIED. `performance.memory` is Deprecated and Non-standard, "only available in Chromium-based browsers"; fields `jsHeapSizeLimit`, `totalJSHeapSize`, `usedJSHeapSize`; "the information this API provides is unreliable"; replacement is `Performance.measureUserAgentSpecificMemory()`. The page does not say whether WebAssembly memory is counted. [MDN: Performance.memory](https://developer.mozilla.org/en-US/docs/Web/API/Performance/memory)
- VERIFIED. `measureUserAgentSpecificMemory()` estimates memory "including all its iframes and workers"; "your document must be in a secure context and cross-origin isolated" (`crossOriginIsolated`); results are "highly implementation dependent" and not comparable across browsers or versions; marked Experimental and not Baseline. [MDN: measureUserAgentSpecificMemory](https://developer.mozilla.org/en-US/docs/Web/API/Performance/measureUserAgentSpecificMemory)
- VERIFIED. `WEBGL_debug_renderer_info`: `UNMASKED_VENDOR_WEBGL` = "Vendor string of the graphics driver", `UNMASKED_RENDERER_WEBGL` = "Renderer string of the graphics driver"; "Depending on the privacy settings of the browser, this extension might only be available to privileged contexts or not work at all"; Firefox disables it under `privacy.resistFingerprinting`. [MDN: WEBGL_debug_renderer_info](https://developer.mozilla.org/en-US/docs/Web/API/WEBGL_debug_renderer_info)
- VERIFIED. Compute Pressure API: launched in Chrome 125; "In the current version of Compute Pressure, only "cpu" is supported"; "thermals" is listed only as a possible future source; `PressureObserver.knownSources` returns the user agent's known source types; `sampleInterval` in ms; the page does not say which platforms (desktop vs Android) expose it. [Chrome for Developers: Compute Pressure API](https://developer.chrome.com/docs/web-platform/compute-pressure)
- VERIFIED. Unity's Web template config: `devicePixelRatio` "enables forcing the DPI scaling ratio for the rendered page. Set to 1 to force rendering to "standard DPI" (or non-Retina DPI), which can help performance on lower-end mobile devices"; `matchWebGLToCanvasSize` syncs the WebGL render target to the DOM size, set false to control both manually. [Web template build configuration and interaction](https://docs.unity3d.com/6000.6/Documentation/Manual/web-templates-build-configuration.html)

### Inferences
- INFERRED. When the Performance panel is attached to the phone through chrome://inspect, the trace is the phone's real execution; leave CPU throttling at "No throttling". The throttling presets exist to emulate a phone from a desktop and would double-count.
- INFERRED. In a Unity Web trace the main-thread flame chart will be dominated by one long WebAssembly frame per `requestAnimationFrame` callback; the useful signals are (a) the gap between the end of that task and the next frame boundary (idle = not CPU bound), (b) the GPU track staying busy past the main task (GPU bound), (c) periodic spikes of equal size (GC, see Key question 3), and (d) Frames-track red/yellow frames aligned with network events in the Network panel (network stalls).
- INFERRED. `performance.memory.usedJSHeapSize` does not report the WASM linear memory where Unity's heap lives; Unity's Diagnostics Overlay shows the WASM heap separately and is the better in-page memory gauge. Use `performance.memory` only as a JS-side sanity check.
- INFERRED. Run `gl.getParameter(debugInfo.UNMASKED_RENDERER_WEBGL)` once in the DevTools console on the phone: "Mali-G52" identifies a Helio G85 class device (Redmi 12C), "Adreno (TM) 610" identifies a Snapdragon 680 device (Redmi 10C / Note 11), "Mali-G57" a Helio G99 / Dimensity 700 device (Redmi 11 Prime). This resolves the "Redmi 11C" label faster than any spec sheet.

### Gaps
- UNKNOWN. Whether Chrome on Android exposes the Compute Pressure "cpu" source at all (the Chrome doc does not say); check `PressureObserver.knownSources` on the phone.
- UNKNOWN. Whether Chrome's unmasked renderer string on Android is shortened for fingerprinting reasons; MDN says nothing about Chrome masking, so treat the string as the raw driver string until tested.

## Key question 3: Known Unity 6 Web-on-mobile performance constraints (threads, Burst, WebGL 2, textures, memory, code size, power preference, official mobile support status)

### Takeaway
Unity 6 officially "Added support for mobile browsers" (Chrome 58+ on Android, iOS Safari 15+) but all game C# runs on one thread: managed threads and ordinary C# jobs are unavailable, and only native engine code and `[BurstCompile]` jobs can run on workers, and only if "Enable Native C/C++ Multithreading" is on and the server sends COOP/COEP/CORP headers so SharedArrayBuffer is available. WebGL 2 capability is required, GC runs only at frame end, the WASM heap starts at 32 MB and grows geometrically (default cap 2048 MB, bugs above that in older Chrome), mobile needs ASTC (fallback ETC2), and Unity's own mobile page recommends Disk Size with LTO, Exceptions None, quality Low/Very Low and `devicePixelRatio: 1`.

### Cited Findings
- VERIFIED. Unity 6.0 release notes, Web platform: "Added support for mobile browsers." Also "Added support for WebAssembly 2023 ... includes support for up to 4GB of heap memory" (native exceptions, SIMD, BigInt, non-trapping float-to-int, sign extension) and "Implemented the Emscripten 3.1.38 toolchain." [New in Unity 6.0 LTS](https://docs.unity.com/en-us/engine/6000.6/manual/whats-new/unity6)
- VERIFIED. Unity staff (jamess_unity, Product Director): 16 Oct 2024 "Android and iOS browser support has arrived With Unity 6"; 21 Oct 2024 "The browsers on mobile devices only have access to lower memory limits" and developers need to test on target devices; the WebGPU backend "is still in experimental state, so we do not recommend using it for production." No staff statement about minimum hardware or expected performance was found in the thread. [Unity Discussions: Unity 6 updates for platforms](https://discussions.unity.com/t/unity-6-updates-for-platforms/1529798)
- VERIFIED. Browser compatibility: a supported browser must be "WebGL 2 capable", HTML5 standards-compliant, 64-bit with WebAssembly support. "Unity's Web platform supports some mobile browsers": iOS Safari 15 and newer, "Chrome 58 and newer on Android"; "Older versions might have issues that affect performance or prevent Unity content from running." WebGL 1 is not mentioned on the page. [Web browser compatibility](https://docs.unity3d.com/6000.6/Documentation/Manual/webgl-browsercompatibility.html)
- VERIFIED. Technical limitations: "Web is an AOT platform, so it doesn't allow dynamic generation of code"; "Managed (C#) threads aren't supported on the Web platform"; multithreading exists for "native C/C++ engine code and for C# jobs compiled with the Burst compiler." [Technical limitations](https://docs.unity3d.com/6000.6/Documentation/Manual/webgl-technical-overview.html)
- VERIFIED. Web multithreading intro: managed C# threads unsupported because WebAssembly lacks multithreaded GC; "most APIs in the System.Threading namespace either execute without effect or don't function" (e.g. `Timer` callbacks, `CancellationTokenSource` timeouts); requires a secure context plus response headers `Cross-Origin-Opener-Policy: same-origin`, `Cross-Origin-Embedder-Policy: require-corp`, `Cross-Origin-Resource-Policy: cross-origin`, otherwise browsers disable SharedArrayBuffer; the Player setting is "Enable Native C/C++ Multithreading" (Publishing Settings) and it enables both native and Burst threading. [Introduction to Web multithreading](https://docs.unity3d.com/6000.6/Documentation/Manual/web-multithreading-intro.html)
- VERIFIED. Burst on Web: "requires Burst compiler package version 1.8.26 or newer"; jobs with `[BurstCompile]` run on worker threads, jobs without it run on the main thread; "you must schedule all jobs from the main thread"; standard C# jobs are restricted to the main thread because of GC limitations; advice: schedule Burst jobs in `Update()`, complete them in `LateUpdate()`, avoid non-Burst jobs depending on Burst jobs (forces an early sync). [Multithreading with Burst in Unity Web](https://docs.unity3d.com/6000.6/Documentation/Manual/web-multithreading-burst.html)
- VERIFIED. Performance page: "Web performance is close to native apps on the GPU"; "the CPU side dispatch of WebGL operations is slower than in native OpenGL"; "avoid large numbers of draw calls per frame"; "standard C# jobs are limited to the main thread"; "SIMD on the web is supported as part of WebAssembly 2023 feature set"; "Unity assumes a display rate of 60 fps for all browsers"; leave `Application.targetFrameRate` at the default -1 unless you want to throttle; hidden tabs update "once per second in most browsers". [Web performance considerations](https://docs.unity3d.com/6000.6/Documentation/Manual/webgl-performance.html)
- VERIFIED. Memory: the heap "can expand up to 16 GB depending on the Maximum Memory Size set in Player settings"; automatic resizing "can cause your application to crash if the browser fails to allocate a contiguous memory block"; "The default options are configured to work well for all desktop use cases"; "for mobile browsers you need to use the advanced tuning options"; "it's recommended to configure the Initial Memory Size to the typical heap usage of the application"; "the garbage collector can only run when no managed code is executing" and "only runs at the end of each program frame"; per-frame temporary allocations cause "a temporary quadratic memory growth pressure for the garbage collector." [Memory in Unity Web](https://docs.unity3d.com/6000.6/Documentation/Manual/webgl-memory.html)
- VERIFIED. Web Player settings: Initial Memory Size default 32 MB; Maximum Memory Size default 2048 MB ("the recommended setting"), up to 16384 MB allowed but "Firefox and Chrome have known bugs above 2048 MB"; Memory Growth Mode None / Linear (step 16 MB default) / Geometric (factor 0.2, cap 96 MB per step; Geometric recommended); "Enable Native C/C++ Multithreading" requires a browser with WebAssembly threads (SharedArrayBuffer); Target WebAssembly 2023 on by default and not recommended off; Enable Exceptions options from None to Full With Stacktrace (the latter "reduces performance and increases memory"); Power Preference: "Set a preference for which GPU to use when rendering on a multi-GPU device", "The browser might ignore this"; Texture compression format DXT / ETC2 / ASTC. [Web Player settings](https://docs.unity3d.com/6000.6/Documentation/Manual/class-PlayerSettingsWebGL.html)
- VERIFIED. Recommended Player settings: Enable Exceptions = None for release ("best performance and smallest builds"); Target WebAssembly 2023 = enable; Managed Stripping Level High; IL2CPP Code Generation "Optimize for code size and build time" (can reduce runtime performance); Debug Symbols Off ("Debug symbols can slow down your application"); Maximum Memory Size: "Unity Web supports up to 4096 MB of memory", "For most applications, 2048 MB of memory is enough", "known bugs for builds over 2048 MB in Firefox and Chrome browsers before version 119." [Recommended Player settings to optimize your Web build](https://docs.unity3d.com/6000.6/Documentation/Manual/web-optimization-player.html)
- VERIFIED. Build settings Code Optimization: Shorter Build Time (default), Runtime Speed, Runtime Speed with LTO, Disk Size ("recommended for mobile browsers with WebAssembly file size limits"), Disk Size with LTO. Texture Compression: ETC2 and ASTC "Widely supported on mobile devices", DXT "Widely supported on desktop devices." [Web build settings reference](https://docs.unity3d.com/6000.6/Documentation/Manual/web-build-settings.html)
- VERIFIED. Texture compression page: desktop and mobile support different formats; without native support "Unity uses a software fallback to decompress the textures at runtime" which "uses more memory and might run slower"; sample script builds `WebGLTextureSubtarget.DXT` (desktop) and `WebGLTextureSubtarget.ASTC` (mobile) and `index.html` loads the ASTC data file when `WEBGL_compressed_texture_astc` is present. [Texture compression in Web](https://docs.unity3d.com/6000.6/Documentation/Manual/webgl-texture-compression.html)
- VERIFIED. Mobile page: disable Development Build and use "Disk Size with LTO" for releases or performance testing; Brotli ("Chrome and Firefox only natively support Brotli compression over HTTPS"); Addressables to load on demand; compress audio; "Use ASTC compressed textures where possible", ETC2 where ASTC is unsupported, ASTC 8x8 as a size/quality balance; set the quality level to Low or Very Low. The page states no hardware minimums, no memory or frame-rate numbers. [Optimize Web platform for mobile](https://docs.unity3d.com/6000.6/Documentation/Manual/web-optimization-mobile.html)
- VERIFIED. Photon Quantum 3 WebGL page (fetched with browser headers after the plain fetch hit a Gcore bot-check): "In general, performance is expected to be lower compared to other platforms"; "build both the Quantum code project in Release mode and set Unity to IL2CPP. Debug builds of the quantum code project can be extremely slow on WebGL"; "Older versions of Unity only support single-threading in WebGL builds, where the simulation is confined to the main thread and the ThreadCount setting in the SimulationConfig is ignored. Starting with Unity 6, multithreading was introduced as an experimental feature and can be enabled through PlayerSettings"; LTO known issue: "RuntimeError: unreachable errors in runtime when Quantum does compression", fix = latest 3.0/3.1 SDK plus `com.unity.sharp-zip-lib`; set Stack Trace for Warning and Log to None; LUT files as Addressables (`QUANTUM_ENABLE_ASYNC_LUT_LOADING`); "Browsers cannot establish direct UDP connections, so WebSockets over TCP are utilized instead ... TCP's reliable and sequenced transfer protocol can negatively impact gameplay for players with poor network connections." [Photon Quantum 3: WebGL](https://doc.photonengine.com/quantum/current/manual/webgl)

### Inferences
- INFERRED. In this project's configuration (Quantum simulation + Unity rendering, single main thread unless native multithreading plus COOP/COEP are enabled), a "lag" at a given scene load is first a main-thread budget problem: Quantum tick + Unity Update + animation + rendering dispatch (slow CPU-side WebGL dispatch) + GC all share one 16.7 ms (or 33 ms) slot. The protocol must therefore split main-thread time, not just measure FPS.
- INFERRED. Burst multithreading only helps code the project explicitly puts into `[BurstCompile]` jobs; it does nothing for Quantum's deterministic simulation unless Quantum itself is configured for it (Photon calls Unity 6 Web multithreading "experimental"). Do not count on it for the first diagnosis; measure with it off, then test with it on if the server already sends COOP/COEP headers.
- INFERRED. Initial Memory Size 32 MB on a phone means the heap will grow in geometric steps during the first match; each growth is a browser reallocation of a contiguous block and a candidate for a one-off hitch. Setting Initial Memory Size to the observed steady-state WASM heap (read it from the Diagnostics Overlay) removes that variable.
- INFERRED. Power Preference is a multi-GPU hint; phones have one GPU, so it has no diagnostic value on Android.
- INFERRED. A texture format mismatch (DXT build served to Android) is a silent CPU and memory tax ("software fallback"); verify the served data file is the ASTC (or ETC2) one before any other test.

### Gaps
- NOT FOUND. An official Unity statement of minimum mobile hardware or expected frame rate for Unity 6 Web: the staff post of Oct 2024 promised guidance, and none of the 6000.6 pages read here contain it.
- NOT FOUND. Any Photon (Fusion or Quantum) page giving expected WebGL mobile frame rates, tick rates, or device tiers; the Quantum WebGL page says only "lower" and "test in WebGL builds."
- UNKNOWN. Whether Chrome on Android serves Unity Web with ANGLE or the native GLES driver on these SoCs (affects dispatch cost); not covered by the Unity or Chrome pages read.

## Key question 6: Thermal throttling detection on Android via Chrome, and how to approximate it

### Takeaway
A web page cannot read temperature or thermal status: Chrome's Compute Pressure API exposes only a "cpu" pressure source (thermals is a future source), and nothing else in the web platform reports it. With the phone already on USB for chrome://inspect, `adb shell dumpsys thermalservice` prints the framework's thermal status (0 NONE to 6 SHUTDOWN) and HAL temperatures on Android 10+, and `/sys/class/thermal/thermal_zone*/temp` gives millidegree-Celsius readings where readable. Without adb, repeat the identical measurement after 10 minutes of sustained load and treat a degradation at constant workload as the thermal signature.

### Cited Findings
- VERIFIED. Compute Pressure in Chrome: only "cpu" supported; "thermals" listed as possible future source; the API offers "high-level states" rather than hardware metrics. [Chrome for Developers: Compute Pressure API](https://developer.chrome.com/docs/web-platform/compute-pressure)
- VERIFIED. Android framework thermal APIs (Android 10 and higher): `PowerManager.getCurrentThermalStatus()`, `addThermalStatusListener()`; status codes `THERMAL_STATUS_NONE` (0), `LIGHT` (1), `MODERATE` (2), `SEVERE` (3), `CRITICAL` (4), `EMERGENCY` (5), `SHUTDOWN` (6); Thermal HAL 2.0 (HIDL) on Android 10 to 13, AIDL `IThermal` on Android 14+; Thermal HAL 1.0 polling only on Android 9 and lower. [AOSP: Thermal mitigation](https://source.android.com/docs/core/power/thermal-mitigation)
- VERIFIED. AOSP `ThermalManagerService.dump()` prints `IsStatusOverride:`, `Thermal Status: <mStatus>`, `Cached temperatures:`, `HAL Ready:`, `Current temperatures from HAL:`, `Current cooling devices from HAL:` (main branch, lines 803 to 818 at fetch time). [AOSP: ThermalManagerService.java](https://android.googlesource.com/platform/frameworks/base/+/refs/heads/main/services/core/java/com/android/server/power/ThermalManagerService.java)
- VERIFIED-EXCERPT. A Stack Exchange answer shows `adb shell dumpsys thermalservice` output on an Android 12 Samsung with "Thermal Status", cached temperatures, HAL Ready and current temperatures, and reports that the command produced nothing on Android 9 and 8.1 devices (HAL 1.0 era). [Android Stack Exchange mirror](https://backiee.wasmer.app/https_android_stackexchange_com/a/246775)
- VERIFIED. Linux kernel ABI: `/sys/class/thermal/thermal_zoneX/temp`: "Current temperature as reported by thermal zone (sensor). Unit: millidegree Celsius. RO, Required." [Linux: Documentation/ABI/testing/sysfs-class-thermal](https://git.kernel.org/pub/scm/linux/kernel/git/torvalds/linux.git/plain/Documentation/ABI/testing/sysfs-class-thermal)
- VERIFIED. `/sys/class/thermal/thermal_zone[0-*]/type` = "Type of the thermal zone"; `/sys/class/thermal/cooling_device[0-*]/cur_state` = "Current cooling state of the cooling device". [Linux: Generic Thermal Sysfs driver How To](https://www.kernel.org/doc/html/latest/driver-api/thermal/sysfs-api.html)

### Inferences
- INFERRED. Measurement loop while a run is in progress (phone on USB): every 10 s run `adb shell dumpsys thermalservice | grep -E "Thermal Status|Current temperatures" -A3` and `adb shell "for z in /sys/class/thermal/thermal_zone*; do echo \$(cat \$z/type) \$(cat \$z/temp); done"`; log alongside the in-game frame-time sampler timestamps. A rise of `Thermal Status` from 0 to 1 or more that coincides with the p95 frame time rising at constant scene load is the thermal attribution. Sysfs read permission varies per OEM (UNKNOWN for Xiaomi); `dumpsys` is the more portable of the two.
- INFERRED. Without adb: run the baseline scene for 5 minutes cold (phone idle 10 minutes beforehand, screen brightness fixed, charger disconnected), then keep the same scene running and record the same 5-minute window again after 10 minutes of continuous play. Same load, worse distribution in the second window = throttling (or memory growth; check the Diagnostics Overlay WASM heap to separate the two).

## Key question 7: A short, comparable attribution protocol and a representative 3v3 MOBA load (how to fake it locally for a fair engine comparison)

### Takeaway
Attribute by ablation, not by guessing: one Release build with Frame Timing Stats and the Diagnostics Overlay, one Development build for the Profiler, a deterministic scripted load, and five variants (baseline, rendering stripped, half-resolution, simulation-only, no bots, local vs networked), each measured as p50/p95/p99 of `Time.unscaledDeltaTime` plus `cpuMainThreadFrameTime` and WASM heap over 5 minutes, repeated after 10 minutes for thermal. The variant that moves the p95 names the bottleneck. This section is protocol design (INFERRED) built on the verified capabilities above; the MOBA load composition is the user's specification, not a sourced figure.

### Cited Findings
- VERIFIED. Tools the protocol relies on and their documented limits: Profiler only in Development builds, Frame Debugger unavailable on Web ([Profile a Web build](https://docs.unity3d.com/6000.6/Documentation/Manual/web-profile.html)); FrameTimingManager always on in Development builds, "Frame Timing Stats" or a `ProfilerRecorder` enables it in Release, no GPU time on WebGL, four-frame delay ([FrameTimingManager](https://docs.unity3d.com/6000.6/Documentation/ScriptReference/FrameTimingManager.html)); `Recorder` only valid in Development Players ([Recorder](https://docs.unity3d.com/6000.6/Documentation/ScriptReference/Profiling.Recorder.html)); `GetTotalAllocatedMemoryLong` returns 0 without the Profiler ([GetTotalAllocatedMemoryLong](https://docs.unity3d.com/6000.6/Documentation/ScriptReference/Profiling.Profiler.GetTotalAllocatedMemoryLong.html)); Diagnostics Overlay in Release builds with JS and WASM heap, 10 s average FPS and "unusually long" frame counter ([Web Player settings 6000.0 excerpt](https://docs.unity3d.com/6000.0/Documentation/Manual/class-PlayerSettingsWebGL.html)); GC runs only at frame end, temp allocations create quadratic GC pressure ([Memory in Unity Web](https://docs.unity3d.com/6000.6/Documentation/Manual/webgl-memory.html)); `devicePixelRatio: 1` helps lower-end mobile ([Web template build configuration](https://docs.unity3d.com/6000.6/Documentation/Manual/web-templates-build-configuration.html)); Chrome Performance panel Main/Frames/GPU tracks on the device via chrome://inspect ([Remote debug Android devices](https://developer.chrome.com/docs/devtools/remote-debugging), [Performance reference](https://developer.chrome.com/docs/devtools/performance/reference)); Photon on WebGL uses WebSockets over TCP, and Quantum debug code builds are "extremely slow" on WebGL ([Photon Quantum 3: WebGL](https://doc.photonengine.com/quantum/current/manual/webgl)); performance testing on mobile should use a non-Development, Disk Size with LTO build ([Optimize Web platform for mobile](https://docs.unity3d.com/6000.6/Documentation/Manual/web-optimization-mobile.html)).
- VERIFIED. "Older versions of Unity only support single-threading in WebGL builds, where the simulation is confined to the main thread and the ThreadCount setting in the SimulationConfig is ignored." [Photon Quantum 3: WebGL](https://doc.photonengine.com/quantum/current/manual/webgl)

### Inferences
- INFERRED. Build matrix (two builds, same commit):
  - R (Release-measure): Development Build off, Code Optimization "Disk Size with LTO" (or "Runtime Speed with LTO" as a second data point), Enable Exceptions None, Debug Symbols Off, Stack Trace Log/Warning None, Target WebAssembly 2023 on, Texture compression ASTC (verify the served data file), Quality Low, template `devicePixelRatio` forced (1 for the low-res variant, default for baseline), Player setting "Frame Timing Stats" on, "Show Diagnostics Overlay" on, Run In Background on, Quantum code project in Release. This is the only build whose numbers count.
  - D (Development-attribute): same, plus Development Build and Autoconnect off (connect by IP:port from the phone's Profile button), Deep Profiling off. Used to read the Profiler's CPU module (Update vs Quantum tick vs Rendering vs GC.Collect samples) and the Memory module, never for absolute numbers.
- INFERRED. In-game sampler (ships in both builds, under a URL flag): a ring buffer of `Time.unscaledDeltaTime` per frame; every 60 s compute p50/p95/p99 and the count of frames over 33 ms and over 50 ms; read `FrameTimingManager.CaptureFrameTimings()` + `GetLatestTimings()` for `cpuFrameTime`, `cpuMainThreadFrameTime`, `cpuRenderThreadFrameTime`, `cpuMainThreadPresentWaitTime` (ignore `gpuFrameTime`, always 0 on Web); read `Profiler.GetTotalAllocatedMemoryLong()` / `GetTotalReservedMemoryLong()` (non-zero only in D) and `System.GC.GetTotalMemory(false)`; emit one JSON line per minute via `Debug.Log` (visible in the chrome://inspect console and copyable) and in a `Recorder("GC.Collect")`-style sampler in D if the sampler name is valid (`isValid`). Discard the first 30 s (warm-up, JIT-free but asset streaming, and the Android first-frame `unscaledDeltaTime` quirk).
- INFERRED. Scripted load, identical in every variant and in both engines: a deterministic bot script (fixed seed) drives 6 heroes (3v3) on fixed paths with ability casts on a timer, 9 to 12 minions per wave on lanes, 2 towers firing, and a steady projectile rate; the camera follows a fixed spline over the same 5 minutes; no human input except in the "touch drag" sub-variant. Record wall time, scene name, build id, variant id, device model string, WebGL renderer string, Chrome version, battery level and charger state at start.
- INFERRED. Variants and what each one isolates (run each for 5 minutes, phone cold, same order on both engines):
  1. BASE: full scene, networked (Photon), bots on, default resolution.
  2. HALF-RES: BASE with `devicePixelRatio: 1` (or `Screen.SetResolution` at half the DOM size with `matchWebGLToCanvasSize` false, or URP Render Scale 0.5). p95 falls by a large fraction = fill-rate / GPU bound (consistent with a shrinking `cpuMainThreadPresentWaitTime`). No change = not GPU bound.
  3. NO-RENDER: BASE with the main camera disabled (or `Camera.enabled = false` and UI off), simulation and bots still running. Frame time that stays high = CPU main thread: Quantum tick, Unity Update, animation, physics. Frame time that drops to a few ms = rendering dispatch dominated (CPU-side WebGL dispatch is slower than native per Unity's performance page).
  4. NO-BOTS: BASE with bot AI disabled (units idle, still rendered). Delta between BASE and NO-BOTS is the AI and pathing cost.
  5. SIM-ONLY: NO-RENDER plus bots, no network (local Quantum session or single-player offline mode). Compare with 3: a difference is the network stack (WebSocket receive, deserialization, snapshot application, prediction/rollback).
  6. LOCAL vs NET: BASE offline vs BASE on Wi-Fi vs BASE on 4G. Stutter that appears only on 4G or correlates with Network-panel gaps in the Chrome trace is transport (TCP over WebSocket, Photon's own caveat), not rendering.
  7. HEAT: repeat BASE after 10 minutes of continuous BASE; log `dumpsys thermalservice` every 10 s. Degradation at identical load with Thermal Status above 0 = throttling.
  8. MEMORY: watch the Diagnostics Overlay WASM heap during BASE; a sawtooth with periodic spikes in the frame-time series aligned with heap drops = GC; a staircase that never comes back = growth; set Initial Memory Size to the plateau and re-run BASE to see whether the growth hitches disappear.
- INFERRED. Decision table from the p95 deltas (same device, same build, same 5-minute script): HALF-RES wins by the most = GPU; NO-RENDER wins by the most = rendering CPU dispatch / draw calls (reduce draw calls, batching, no post-processing, no extra render targets on Mali); NO-BOTS or SIM-ONLY wins = simulation / AI on the main thread (profile with D to split Quantum tick from Unity Update); periodic spikes aligned with heap drops = GC (hunt per-frame allocations); only networked runs stutter = network; only the second run after heating stutters = thermal; only the touch-drag sub-variant stutters = the Chrome Android touch-input issue.
- INFERRED. Fairness rules for comparing two engines or two architectures: same phone, same Chrome version, same scene composition and bot script, same 5-minute camera path, same resolution policy (`devicePixelRatio` fixed), same build flavour (Release, LTO, exceptions off), phone cooled 10 minutes between runs and charger unplugged, three repetitions per variant, report p50/p95/p99 and the count of frames over 50 ms rather than average FPS (the Diagnostics Overlay's 10 s average FPS hides spikes). Any run where the WASM heap grew past the Initial Memory Size is flagged, because heap growth events are not comparable between engines with different allocation patterns.
- INFERRED. Why "representative 3v3" is 6 heroes, 9 to 12 minions, 2 towers and projectiles: this is the user's own target scene, not a sourced industry figure; what matters for comparability is that both engines run exactly this entity count with the same animator, VFX and collider budgets per entity, so the comparison measures engine overhead, not content.
