## The architect's four questions, answered first: (a) refuse a player, (b) force the loadout, (c) trustworthy result, (d) server-side replay

### Takeaway
On Public Cloud: (a) **yes**, a backend can refuse a player at three gates (custom-auth connect, JoinGame/CreateGame webhook, AddPlayer webhook), each carrying a backend-set `UserId` and the secret `AuthCookie`; (b) **yes**, the AddPlayer webhook response **replaces** the client's `RuntimePlayer` entirely, and GameConfigs/CreateGame responses replace `RuntimeConfig` and `SessionConfig`; (c) **no** server-computed result exists on Public Cloud: the GameResult webhook is an aggregation of **client-submitted** results that Photon itself labels "untrusted client input"; a server-generated result (`IsServerResult: true`) requires Enterprise Cloud server simulation; (d) **yes**, the Public Cloud server streams the authoritative input history (ReplayStart + ReplayChunk webhooks, described by Photon as "a trusted source") and Photon documents re-simulating it headless with the .NET console runner, but assembling the replay, running it and extracting the result is the developer's code.

### Inferences
- **"Server confirms the input stream" vs "server computed the result"** (INFERRED from the verified quotes above): on Public Cloud the Quantum server is the sole arbiter of *which inputs exist at which tick* (it expires frames, replaces missing inputs, delta-compresses and streams the final per-tick input set), so the replay stream is authoritative about *inputs*. It never executes the game simulation on Public Cloud, so nothing Photon sends is authoritative about *state* or *outcome*. Trustworthy outcome on Public Cloud therefore equals: trusted inputs (webhook) + trusted configs (webhook overrides) + trusted code (your own build) + your own re-simulation. The GameResult webhook is only a cheap first-pass signal (majority vote among clients) and an index to decide which matches to re-simulate.
- A "player must own NFT X" rule is implementable entirely in the backend at the AddPlayer hook: look up `UserId`/`AuthCookie`, check ownership, return 400 (`WebhookError`) or 200 with a server-built `RuntimePlayer` whose loadout fields reference only assets the player owns (INFERRED; the mechanics are VERIFIED).

### Gaps
- Photon does not document any latency figure for the three hooks; it only warns that requests are serialised per room (see question 1).
- No doc page states an SLA or guarantee that every ReplayChunk is delivered; the retry policy (3 retries, 10 s timeout) is the only statement.

## Question 2: GameResult webhook: content, producer, trustworthiness; server-side input archive vs client uploads

### Takeaway
GameResult is produced by **clients** (each sends one `GameResult` JSON from inside the simulation), aggregated by the Quantum server by identical content and delivered once at room close with a per-result list of submitting clients; Photon says to treat it as untrusted. The server-side input archive exists as a push stream (ReplayStart/ReplayChunk webhooks); there is no pull API and no client upload needed for inputs.

### Cited Findings
- **Producer and timing.** "Using the GameResult Quantum event in the simulation will trigger the upload of a GameResult instance by clients to the Quantum server once per game." "The game result event can be invoked once per game by each client, which is triggered from inside the simulation by calling the GameResult Quantum event. The actual webhook is launched when the room is disbanded and closed." Code: `f.Events.GameResult(new GameResult { Winner = 3 });` with the partial class pattern `public partial class GameResult { public int Winner; }` in `GameResult.User.cs`. "Because lingering clients and RoomTTL can prolong closing the room, there can be a delay between the game ending and the result webhook." VERIFIED. [Source](https://doc.photonengine.com/quantum/current/manual/webhooks)
- **Aggregation = grouping by identical payload, sorted by vote count.** "The results are combined by each different submitted result. Ideally only one because every client send the same data. The result list is sorted by the number of players that submitted it and can be used to perform a simple majority vote to slightly increase the correctness of the result." VERIFIED. [Source](https://doc.photonengine.com/quantum/current/manual/webhooks)
- **Payload.** `POST /game/result` with `AppId`, `GameId`, `Results: GameResultInfo[]`; each `GameResultInfo` = `Result` (the game-specific JSON, `$type` "Quantum.GameResult, Quantum.Simulation", with built-in `Frame`), `Clients: GameResultClientInfo[]` (`UserId`, `ActorNr`, `Players: int[]` "The list of players that this user controls", `GameTime` "The timestamp when the result reached the server", `AuthCookie`), `IsServerResult` ("Has this result been generated by server simulation"). Notes: "supports both standard JSON format and binary payloads using base64 encoding", "Dictionaries are not supported, due to Unity serialization limitations". VERIFIED. [Source](https://doc.photonengine.com/quantum/current/manual/webhooks)
- **Trust statement.** "The Json content forwarded by the Quantum server should be handled as untrusted client input". `IsServerResult: false` in the Public Cloud example. VERIFIED. [Source](https://doc.photonengine.com/quantum/current/manual/webhooks)
- **Delivery reliability from the client side.** "The client can register the Quantum callback CallbackGameResultResponse to queue up leave game behaviour. This makes sure that the client successfully send the game result data and it was received by the Quantum server. Shutting down the simulation or disconnecting the client around the same time the GameResult event was evoked leads to incomplete server communication." VERIFIED on the page; but `CallbackGameResultResponse` is listed as **new in the 3.1 preview** ("Added a new Quantum callback `CallbackGameResultResponse` to react to completed game result operations", Build 2142, Jul 17, 2026) and a grep of the project's SDK 3.0.9 finds **0** occurrences, so it is not available to this project today. [Source](https://doc.photonengine.com/quantum/current/manual/webhooks); [Source](https://doc.photonengine.com/quantum/v3/getting-started/preview-3-1/sdk-download)
- **Server-side forcing of result upload.** CreateGame response `SendGameResultSec`: "Force sending the game results (if exists) after the game time elapsed in second." VERIFIED. [Source](https://doc.photonengine.com/quantum/current/manual/webhooks)
- **Plugin-side fixes relevant to result integrity.** Plugin SDK 3.0.9 (Build 70, Dec 17, 2025): "Fixed an issue that caused the game result webhook to be send for games that never started a game session". Plugin SDK 3.1.0 (Build 84, Jul 16, 2026): "Fixed an issue that caused the GameResult webhook to not include client AuthCookies" and "Adding ActorNr and AuthCookie to the game result webhook client information". VERIFIED. [Source](https://doc.photonengine.com/quantum/current/addons/plugin-sdk/overview)
- **Server-side input archive: push stream, no pull.** ReplayStart (`POST /replay/start`): "sent when the simulation and the input recording is starting on the server. It's is a trusted source for capturing the game replay directly from the server instead of relying on clients to send it to a developers backend." "A response has to be received by the Quantum server before it is sending its first replay slice or the replay recording will be canceled." Request includes `SessionConfig` ("The SessionConfig that the simulation started with.") and `RuntimeConfig` ("The GZipped Json of the RuntimeConfig that the simulation started with."). Response `{ "Skip": true }` disables streaming for that session. The input for each tick has a leading int describing the data length."). "Replay streaming will be disabled after the ReplayChunk webhook returns an error" (plugin 3.0.9). VERIFIED. [Source](https://doc.photonengine.com/quantum/current/manual/webhooks); [Source](https://doc.photonengine.com/quantum/current/addons/plugin-sdk/overview)
- **Server input history is bounded.** "input history stored on the server is limited to ~10 minutes." VERIFIED. [Source](https://doc.photonengine.com/quantum/v3/manual/game-session/reconnecting)

### Inferences
- Whether the Public Cloud GameResult payload currently includes `AuthCookie`/`ActorNr` per client depends on which plugin build Photon runs in Public Cloud; the fix is listed under plugin SDK 3.1.0 Build 84 only. Treat their presence as UNKNOWN until observed in a real payload; the `UserId` field is documented in all versions.
- The "majority vote" is only as strong as the number of distinct honest clients; in a 1v1 or small-team MOBA a single cheater produces a split vote with no majority, so the backend needs the re-simulation path (question 3) as the tie-breaker (INFERRED).
- A GameResult can be absent (crash, Alt+F4, no client reached the event). The input stream still arrives via ReplayChunk `IsLast`, so re-simulation is the only outcome source in that case (INFERRED).

### Gaps
- Not found in docs: any server-side signature, hash or tick-anchored proof attached to the client-submitted `GameResult`.
- Not found in docs: an HTTP endpoint to *request* a replay/input history from Photon after the fact; only the push webhooks exist.
- Not found in docs: whether ReplayChunk delivery is guaranteed in order or how gaps are signalled beyond `ChunkNumber`/`TickCountTotal`.

## Question 3: Replay and verification: .NET runner, what a replay needs, checksums, documented headless re-simulation

### Takeaway

## Question 4: Custom authentication with Quantum 3 / Realtime 5: flow, what the auth service receives, how UserId/AuthCookie reach the session and webhooks, trustworthiness

### Takeaway
Custom Authentication is a Public Cloud feature where Photon calls your HTTPS endpoint (GET query string or POST body) at connect time; your `ResultCode 1` response can set `UserId` (overrides the client, immutable for the session), `Nickname`, a secret `AuthCookie` (never visible to clients, forwarded in every Quantum webhook) and public `Data`; the backend-set `UserId` is the identity that webhooks and the GameResult client list carry, and other clients only see it if `PublishUserId` is true.

### Cited Findings
- **What it is.** "a Custom Authentication Provider is a web service, built and managed by you. The Photon server gets set up to pass authentication values to a configured URL and wait briefly for a response. Depending on the result, the client can connect to Photon or gets rejected. In best case, a userID is defined by the backend and optionally additional info can be passed in a secure way to be used in Server Plugins." Flow: "The Photon server calls the authentication provider with the authentication info passed with Connect()." Quantum: "Custom Authentication: Photon does not offer player accounts and recommends securing the logins using a proprietary or third-party authentication provider and set up Photon Custom Authentication." VERIFIED. [Source](https://doc.photonengine.com/realtime/current/reference/custom-authentication); [Source](https://doc.photonengine.com/quantum/v3/manual/game-session/starting-session)
- **Dashboard setup.** "you can enter your authentication URL and decide whether clients should be rejected if your authentication service is not online". "Optionally add key/value pairs to be sent to the authentication service with each request as query string parameters." Best practice: dashboard-only secrets such as "API public key to make sure that the request is really coming from one of Photon servers." Anonymous policy: "allow or reject anonymous clients ... The option is shown only when you add at least one authentication provider." VERIFIED. [Source](https://doc.photonengine.com/realtime/current/reference/custom-authentication)
- **What the auth service receives.** "The default HTTP method used in authentication is GET. So, parameters can be sent as key/value pairs in the query string. The final URL will include the \"union\" of the key/value pairs set from client and those set from the dashboard. In case, the same key is used in both places, only the dashboard value will be sent." POST: "setting the AuthenticationValues.AuthPostData field to a value. The latter can be of type string or byte[] or Dictionary<string, object>. In case of Dictionary<string, object>, the payload will be converted to a JSON string and the HTTP request's Content-Type will be set to \"applicaton/json\"." Client code: `authValues.AuthType = CustomAuthenticationType.Custom; authValues.AddAuthParameter("user", userId); ... loadBalancingClient.AuthValues = authValues;`. Encryption: "The first time, the operation sends the actual authentication values as encrypted operation. For subsequent server switches, Photon provides it's own token, which is encrypted and used automatically." VERIFIED. [Source](https://doc.photonengine.com/realtime/current/reference/custom-authentication)
- **Response contract.** `ResultCode` 0 "Authentication incomplete, only Data returned" (OAuth/2-step), 1 success, 2 "Wrong credentials", 3 "Invalid parameters". `UserId`: "This is always forwarded to the client when received by Photon servers. Otherwise, if AuthenticationValues.UserId was not initially set a randomly generated UserId will be sent back to client. Keep in mind that nested arrays or objects are not supported." VERIFIED. [Source](https://doc.photonengine.com/realtime/current/reference/custom-authentication)
- **UserId precedence.** "The UserID for a client can be set in three ways: 1. Client sends its UserID before connecting by setting AuthenticationValues.UserId ... 2. An external authentication provider returns the UserID on successful authentication. This overrides any value sent by the client. 3. Photon Server will assign GUIDs as IDs for users that did not get UserIDs using 1 or 2." "you can't join the same Photon room from two separate clients using the same UserID." Blocklist use: "You can prohibit malicious users from connecting to your applications by keeping a blocklist of their UserIDs and making use of Custom Authentication." VERIFIED. [Source](https://doc.photonengine.com/realtime/current/lobby-and-matchmaking/userids-and-friends)
- **Visibility of UserId to other clients.** "Players can share their UserIDs with each other inside rooms ... it can also be a security concern as random players know the userIDs. The server will provide this information to anyone joining and you can access each player's UserID using Player.UserId." Webhooks `RoomOptions.PublishUserId` "Default is false." VERIFIED. - **How identity reaches the Quantum session and webhooks.** Every player-related webhook carries `UserId` and `AuthCookie` ("Added ActorNr and AuthCookie properties for all player related webhooks", plugin SDK 3.0.1 Build 39). `PlayerAdded` gives the mapping `UserId` -> `ActorNr` -> `Player` (global Quantum player index). [Source](https://doc.photonengine.com/quantum/current/addons/plugin-sdk/overview); [Source](https://doc.photonengine.com/quantum/current/manual/webhooks); [Source](https://doc.photonengine.com/quantum/current/manual/player/player); [Source](https://doc.photonengine.com/quantum/v3/manual/game-session/reconnecting)
- **Token lifetime.** "The authentication ticket expires after 1 hour. It will be refreshed automatically before running out in the course of the Quantum game session". VERIFIED. [Source](https://doc.photonengine.com/quantum/v3/manual/game-session/reconnecting)
- **Quantum 3.1 convenience.** "Added a virtual `Authenticate()` method to the `QuantumStartUIConnection` class to quickly enable custom authentication" (3.1 preview Build 2039, Apr 16, 2026). VERIFIED. [Source](https://doc.photonengine.com/quantum/v3/getting-started/preview-3-1/sdk-download)

### Inferences
- Trust model (INFERRED from the verified contract): a `UserId` is trustworthy **to the backend/webhooks** only if (1) the auth provider sets it in the `ResultCode 1` response and (2) anonymous clients are rejected in the dashboard; otherwise a client can self-assign any `UserId` (path 1) or get a random GUID (path 3). The `AuthCookie` is the strongest channel because the client never sees it: put a signed session token or the wallet address + verification nonce there and validate it in every webhook.
- For a wallet-based game, the natural flow is: client signs a nonce -> auth service verifies the signature -> returns `UserId` = canonical wallet address, `AuthCookie` = { wallet, sessionId, issuedAt } -> AddPlayer webhook checks on-chain ownership for `AuthCookie.wallet` (INFERRED; Photon documents the mechanics, not this mapping).
- Other clients can only learn a peer's `UserId` if `PublishUserId` is enabled; in-simulation identity is the Quantum player index, which the server assigns ("The Quantum player index is assigned by the server based on the order in which the QuantumGame.AddPlayer() operations arrive."). So a client cannot impersonate another player's index, but any identity claim inside `RuntimePlayer` (e.g. a nickname or wallet string) is client data unless replaced by the AddPlayer webhook (INFERRED). [Source](https://doc.photonengine.com/quantum/current/manual/player/player)

### Gaps
- Not found in docs: whether the `AuthCookie` is re-fetched on token refresh or frozen at first authentication (relevant for revoking a player mid-session).
- Not found in docs: maximum size of `AuthCookie`.
- Not found in docs: an explicit statement that the auth provider URL must be HTTPS (the examples use https).

## Question 8: Late join, reconnection, snapshots, and the Public Cloud input relay with input delay/rollback

### Takeaway
On Public Cloud the server never holds game state: late joiners and reconnectors receive a **buddy snapshot** uploaded by another client (or reuse a local snapshot <= 10 s old, up to `EmptyRoomTTL` max 2 min); server-side snapshots exist only with a custom plugin running server simulation; the server's job is clock sync, input delay/time-scale control, input expiry/replacement, delta compression and ~10 minutes of input history.

### Cited Findings
- **Start protocol.** "A StartRequest is send to server attaching the SessionConfig and RuntimeConfig. The request is received by the server, validated and a SimulationStart confirmation is send back to the client containing the chose configs. If the information attached to the request is not valid, the request will be refused by a PluginDisconnect message. The SimulationStart game message is received by the client. Clients do not have a player, yet. They will all start as spectator only and cannot send inputs or commands. (OPTIONAL) - In case of a late join, the client may receive a snapshot-resync. QuantumGame.AddPlayer() is used to register a Quantum player and sending individual RuntimePlayer configs. The server encodes successfully joined players into the input which will be processed by all clients at the same tick". VERIFIED. [Source](https://doc.photonengine.com/quantum/current/manual/player/player)
- **Snapshot sources.** "A client can create its own snapshot when the simulation is still running (local snapshot), the snapshot can be requested from other clients (buddy snapshot) or it can be send down from a custom server plugin that runs the simulation." "Otherwise late-joining or reconnecting clients would have to start the game session from the very beginning and fast-forward through the input history send by the server which can render the client app useless until it caught up and also input history stored on the server is limited to ~10 minutes." "Buddy snapshots are requested for clients connecting 5 seconds after the initial start." "The server uses a load balancing mechanism to decide which client it will ask for a buddy snapshot to not overburden individual clients." ### Inferences
- Security consequence of buddy snapshots (INFERRED): on Public Cloud a late joiner's initial state comes from a *peer*, so a malicious peer selected as snapshot provider could hand a tampered state to a joiner; the server does not validate snapshots against anything (nothing in the docs says it does). This also means the server-streamed replay (inputs from tick 0) remains the only state-independent artifact. `SnapshotsBlocked` in the JoinGame/CreateGame response lets the backend exclude untrusted clients from being providers.
- The "StartFromSnapshot" feature shows the server will accept a client-provided initial `FrameData` as the starting state of an online game; for competitive matches the backend should not allow this (keep `InitialTick` 0 by pinning configs and not using `FrameData`), otherwise the replay would not be reproducible from tick 0 (INFERRED).

### Gaps
- Not found in docs: any server-side validation of buddy or local snapshots (hash, tick check beyond the 10 s age rule).
- Not found in docs: whether `ForceSnapshotsForAllJoiners` is exposed on Public Cloud dashboards.

## Question 9: Consolidated: what Photon provides on Public Cloud vs what remains the developer's job

### Takeaway
Photon Public Cloud provides identity plumbing (custom auth call-out, immutable UserId, secret AuthCookie), admission/override hooks (CreateGame, JoinGame, GameConfigs, AddPlayer), dashboard hardening keys, an aggregated client-result webhook, and a trusted server-side input stream plus the headless runner skeleton; the developer must build the auth service, the webhook backend with the complete `RuntimePlayer`/`RuntimeConfig`/`SessionConfig` JSON, the replay assembler, the version-pinned re-simulation worker with result extraction, and all comparison/adjudication logic.

### Cited Findings
- Photon-side (all VERIFIED above, sources repeated): custom auth proxy and `AuthCookie` channel [Source](https://doc.photonengine.com/realtime/current/reference/custom-authentication); eleven webhooks with 200/400 semantics and complete-object overrides [Source](https://doc.photonengine.com/quantum/current/manual/webhooks); dashboard keys incl. global `SessionConfig`, `MaxPlayerSlots`, `Block*` [Source](https://doc.photonengine.com/quantum/v3/manual/game-session/dashboard-configuration); GameResult aggregation labelled untrusted [Source](https://doc.photonengine.com/quantum/current/manual/webhooks); ReplayStart/ReplayChunk "trusted source" input stream [Source](https://doc.photonengine.com/quantum/current/manual/webhooks); replay file format and `Quantum.Runner.Dotnet` [Source](https://doc.photonengine.com/quantum/current/manual/replay); the documented ladder "Prototyping -> Game Result Webhook -> Resimulation Replays -> Custom Quantum Server" [Source](https://doc.photonengine.com/quantum/current/manual/cheat-protection).
- Developer-side obligations stated by Photon: "a Custom Authentication Provider is a web service, built and managed by you." [Source](https://doc.photonengine.com/realtime/current/reference/custom-authentication); "To make the replays playable in Unity, either serialize them in JSON into a QuantumReplayFile class or create another data structure to store the required data." [Source](https://doc.photonengine.com/quantum/current/manual/replay); "Json data sent by the custom backend has to be deterministically deserializable on every client." [Source](https://doc.photonengine.com/quantum/current/manual/webhooks); "Having a data structure that can be filled with the results to be sent to a backend is the first thing to have." [Source](https://doc.photonengine.com/quantum/current/manual/cheat-protection).

### Inferences
Developer checklist for this project (INFERRED synthesis of the verified facts):
1. Auth service: verify wallet signature, return `UserId` = wallet (canonical case), `AuthCookie` = session claims; dashboard: reject anonymous, reject if provider offline.
2. Dashboard: `WebHookBaseUrl`, `WebHookSecret`, enable OnCreate/OnJoin/OnLeave/OnClose, `WebHookEnableGameConfigs`, `WebHookEnableAddPlayer` (and the `WebHookEnableRuntimePlayer`/`WebHookEnableRuntimeConfig` spellings from the API reference until one is confirmed), `WebHookEnablePlayerAdded`, `WebHookEnablePlayerRemoved`, `WebHookEnableGameResult`, `WebHookEnableReplay` (+ `WebHookReplayUseBinaryRequests`/`WebHookReplayUseCompression` to cut payload), `BlockRoomProperties`, `BlockPlayerProperties`, `BlockNonProtocolMessages`, `MaxPlayerSlots=1`, `CloseRoomAfterStartSec`, global `SessionConfig` JSON.
3. Backend endpoints: `/game/create`, `/game/join` (ownership/ban gate; `ExpectedUsers` for pre-made lobbies), `/game/configs` (return the canonical `RuntimeConfig` + `SessionConfig`), `/player/add` (ownership check per `AuthCookie`; return complete `RuntimePlayer` built from owned assets; 400 `WebhookError` otherwise), `/player/added` and `/player/removed` (persist `UserId`<->`ActorNr`<->`Player` map), `/game/result` (store all result groups, votes), `/replay/start` + `/replay/chunk` (append-only store keyed by `GameId`, honour `ChunkNumber`, `IsLast`), `/game/close`.
4. Re-simulation worker: per build version, keep `Quantum.Simulation.dll` + exported asset DB + LUT; assemble `QuantumReplayFile` (SessionConfig from ReplayStart, RuntimeConfig = gunzip of ReplayStart bytes, input = concatenated chunks); run via `Quantum.Runner.Dotnet` extended to subscribe `EventGameResult` and dump the final verified frame; compare with the GameResult majority; adjudicate; only then write progression/rewards.
5. Client: raise `f.Events.GameResult(...)` exactly once from simulation code at match end; delay leave/shutdown after it (no `CallbackGameResultResponse` in 3.0.9, so use a fixed grace delay or upgrade to 3.1 later); set `ClientId = UserId`; set `PlayerTtl`/`EmptyRoomTtl`.

### Gaps
- Everything in the checklist is unimplemented in Photon's deliverables; Photon ships no sample webhook backend for Quantum 3 in the pages read (the custom-auth page links a GitHub sample for auth providers only; not fetched).
- Whether the Public Cloud plugin currently honours every documented key (see the two naming inconsistencies) must be confirmed with a live test against the AppId.
